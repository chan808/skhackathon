# AI 리터러시 AI Native 역량 준비 조사

조사 기준: 2026년 10월 13일, 한국 시간. 대상: 신청을 마쳤고 웹 개발 경험이 있는 참가자의 1차 예선 준비와 이후 실무 과제 대비.

**당장 준비할 것은 AI 기초 개념의 정확한 구분, AI 답변의 오류를 찾아 고치는 능력, 데이터·코드의 독립 검증이다.** 현재 공개 정보로는 특정 모델·프레임워크 사용법을 깊게 외우는 것보다 이 세 가지의 전이성이 높다. 아래 기술 지도와 학습 시간·모의 점수는 조사자가 설계한 준비 권고이며, 실제 출제 영역·배점·합격선을 뜻하지 않는다.

## 확인된 평가 방향과 아직 확인되지 않은 사항

SK하이닉스는 AI 활용 문제 해결 역량을 평가하며, 온라인 예선에서 AI 기본 활용 역량과 AI 리터러시를 본다고 밝혔다. 문제 정의, AI 활용, 결과 검증을 종합적으로 본다는 점은 공식적으로 확인된다. 그러나 이 표현만으로 특정 알고리즘이나 코딩 과제가 1차에 출제된다고 판단할 수 없다. [SK하이닉스 공식 발표](https://talent.skhynix.com/hub/ko/company/story/237)

대회 단계별 운영사와 공개 체험 정보는 [대회·응시 정보 보고서](./01-event.md)를 우선 참고한다. 조사 중 확인된 중요한 구분은 **1차의 프로그래머스 AI 역량평가 준비와, 크래프톤이 운영하는 2차·본선의 실무 과제 준비를 나눠야 한다는 것**이다. 공개 Cofa-Probe 안내를 그대로 1차 시험 규칙으로 적용하면 준비 방향이 어긋날 수 있다.

현재 확정하지 않는 사항은 다음과 같다.

- 실제 1차의 문항 수, 세부 비중, 제한 시간, 객관식·서술형 구성.
- 시험 중 개인 AI 서비스, 인터넷 검색, IDE, 노트, 추가 모니터, 외부 파일의 사용 가능 여부.
- 제공 모델, 요청 횟수, 토큰 한도, 코드 실행 환경, 설치 가능 패키지.
- SK 대회 과제별 Cofa 감독 조건과 사후 Q&A 시간, 세부 채점표.
- 아래 기술 용어가 그대로 출제되는지, 특정 모델 이름이나 수식이 요구되는지.

**실제 응시 안내와 대회 규정이 이 문서의 준비 권고보다 우선한다.** 이 폴더의 모의 문제·실습은 시험 전에 연습하기 위한 자료다.

## 1차를 앞둔 우선순위

웹 개발 경험이 있다는 전제에서 새로운 웹 프레임워크 학습은 낮은 우선순위다. 이미 아는 API·JSON·SQL·디버깅 지식을 AI 시스템에 연결하는 방식이 효율적이다.

| 우선순위 | 준비 범위 | 완료를 판단하는 기준 | 권장 시간 |
|---|---|---|---|
| P0 | 토큰, logit, 확률, temperature, embedding, hallucination | 서로 다른 개념을 예시로 설명하고 잘못된 단정을 고친다 | 2시간 |
| P0 | 요구사항 해석·프롬프트 개선·AI 답변 검증 | 모호한 요청을 입력·조건·출력·확인 방법으로 바꾼다 | 2시간 |
| P0 | 데이터 해석·SQL·코드 오류 | 중복·누락·분모·타입·경계 조건의 오류를 찾는다 | 3시간 |
| P0 | accuracy/precision/recall와 누설 | 혼동행렬을 계산하고 적절한 평가 조건을 선택한다 | 2시간 |
| P1 | RAG, 검색·생성 분리, 근거 확인 | 검색 실패와 답변 실패를 구분하고 고칠 지점을 정한다 | 1.5시간 |
| P1 | 구조화 출력·도구 호출·권한 | 형식 준수와 의미 정확도, 요청과 실행을 구분한다 | 1.5시간 |
| P1 | 제한된 대화로 문제 해결 | 한 번의 질문에 필요한 자료와 성공 기준을 넣는다 | 2시간 |
| P2 | attention 개념·causal mask | 수식 기호의 역할을 설명한다. 전체 모델 구현은 요구하지 않는다 | 1시간 |
| P2 | 다중 에이전트·fine-tuning·운영 인프라 | 필요한 상황과 추가 비용을 설명하는 수준 | 이후 단계에서 확대 |

모든 항목을 같은 깊이로 공부할 필요는 없다. P0에서 틀리는 부분을 찾으면 P2 학습보다 그 오답을 먼저 수정한다. 1차를 통과한 뒤에는 작은 결과물을 직접 만들고 원리를 설명하는 연습의 비중을 높인다.

## LLM의 작동을 이해할 때 필요한 구분

### 머신러닝 기본 개념 먼저 구분하기

지도학습은 입력과 정답의 관계를 학습하며, 회귀는 수치 예측, 분류는 범주 예측과 연결된다. 비지도학습의 군집은 정답 라벨을 그대로 맞추는 분류와 다르다. 강화학습은 행동의 보상에 따라 정책을 학습한다. 생성형 AI는 콘텐츠를 생성하며 여러 학습 방식이 함께 사용될 수 있다. 이 분류들을 서로 완전히 배타적인 네 상자라고 외우지 않는다. [Google 공식 머신러닝 기초](https://developers.google.com/machine-learning/intro-to-ml/what-is-ml)

과적합은 학습 자료에서는 잘 맞지만 새로운 자료에서는 성능이 떨어지는 현상이다. 학습과 검증 손실의 차이, 데이터 대표성, 모델 복잡도를 점검한다. [Google 공식 과적합 설명](https://developers.google.com/machine-learning/crash-course/overfitting/overfitting)

자체 적용 예시로 생산량 예측은 수치의 단위와 오차, 불량 분류는 목표 클래스와 오탐·미탐, 로그 군집은 사람이 확인한 군집 의미, 작업 순서 결정은 보상과 안전 제약을 먼저 정의한다. 어떤 과제든 LLM 호출 한 번으로 바꾸는 것이 목표가 아니다. 규칙·집계·검색·예측·생성 중 실제 필요한 역할을 골라야 검증 방법도 정할 수 있다.

### 토큰 확률 logit temperature

토큰은 입력·출력을 처리하는 단위이며 단어 수와 일치하지 않는다. 같은 문장도 토크나이저가 다르면 나뉘는 방식이 달라질 수 있다. 특히 한국어 단어 수에 영어의 대략적인 환산 규칙을 그대로 쓰지 않는다. [Hugging Face 토큰화 공식 문서](https://huggingface.co/docs/transformers/main/en/tokenizer_summary)

logit은 정규화 이전의 점수다. 다음 토큰 분포는 softmax 등의 처리로 얻는다. temperature와 top-p는 생성 후보의 선택 분포를 조절한다. temperature를 낮추는 것이 사실 확인이나 최신 지식 업데이트를 수행하는 것은 아니다. 다음 토큰의 확률도 완성된 답변 전체의 사실 정확도와 다르다. [Hugging Face 생성 설정](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation)

자체 연습에서는 다음 문장을 고쳐 본다. “temperature가 낮으니 계산식은 검증하지 않아도 된다”, “token budget은 한국어 단어 수다”, “logit이 0.9면 이 답은 90% 사실이다”. 정답을 외우기보다 각각 어떤 종류의 값을 혼동했는지 말하는 것이 목표다. 생성의 다양성, 모델의 지식, 입력의 길이, 업무의 정답 여부를 서로 다른 축으로 놓아야 한다.

### attention과 causal mask

원 Transformer의 scaled dot-product attention은 Q와 K의 내적으로 관련도를 만들고, 차원에 따라 스케일링하고 softmax를 적용해 V를 가중합한다. 자기회귀 decoder는 미래 위치를 볼 수 없도록 mask를 쓴다. 단어 순서 정보도 표현해야 한다. [Attention Is All You Need 원문](https://arxiv.org/html/1706.03762v7)

이를 준비할 때 모델 전체를 구현하기보다 작은 그림을 직접 그려 본다. “현재 토큰이 앞선 문맥 중 어디를 참고하는가”, “아직 생성하지 않은 정답을 볼 수 있다면 평가가 왜 부당한가”를 설명하면 된다. attention이 검색 엔진 그 자체라거나, 높은 attention 가중치가 곧 사실 검증을 의미한다고 표현하지 않는다. Q·K·V의 역할과 자기회귀 제약을 이해하고 넘어가는 편이 현재 시간 예산에 맞다.

### 사전학습 fine tuning 문맥 활용

언어모델은 대규모 텍스트의 학습으로 통계적 언어 표현을 얻는다. 이후 특정 작업에 맞춰 학습하는 과정과 추론 중 예시를 프롬프트로 제공하는 과정은 구분해야 한다. [Hugging Face Transformer 교육 자료](https://huggingface.co/learn/llm-course/en/chapter1/4)

예를 들어 “분류 예제를 세 개 붙였다”는 사실만으로 모델 가중치가 바뀐 것은 아니다. 실습에서는 입력 예시를 바꿨을 때 답변이 달라지는 현상을 관찰하고, 그것을 영구 학습과 혼동하지 않는 설명을 적는다. 현장 문서가 자주 바뀌는 문제라면 최신 자료의 검색과 제공부터 검토하고, 모델 재학습은 반복 실패의 원인과 데이터·평가 조건이 충분히 확인된 뒤 비교할 선택지로 둔다.

### embedding과 긴 문맥

embedding은 텍스트를 벡터로 표현해 관련성을 비교하는 데 사용한다. 문서 유사도가 높다는 것은 그 문서가 질문과 비슷한 내용을 담을 수 있다는 뜻이며, 내용의 진실성·권한·현행 버전을 확정하지 않는다. [OpenAI 공식 embedding 문서](https://developers.openai.com/api/docs/guides/embeddings)

또한 모델이 긴 입력을 수용하는 것과 모든 근거를 안정적으로 활용하는 것은 별개다. 2023년의 원 연구는 정보 위치에 따라 성능 차이가 날 수 있음을 보여줬다. 모든 2026년 모델이 같은 정도로 실패한다는 뜻으로 일반화하지 말고, 자신의 작업에서 확인할 검증 조건으로 사용한다. [Lost in the Middle 원 논문](https://arxiv.org/abs/2307.03172)

자체 연습으로는 규칙 하나를 문서 앞·중간·뒤에 각각 둔 세 버전을 준비한다. 같은 질문에 답하게 하고 규칙 준수 여부를 비교한다. 중요한 규칙을 명확히 요약하고 관련 자료를 줄이는 조치가 도움이 되는지 확인하되, “문맥 끝에 쓰면 무조건 해결된다” 같은 만능 규칙으로 만들지 않는다.

## 프롬프트 설계보다 중요한 것은 검증 가능한 문제 정의

공식 OpenAI 문서는 지시, 예시, 맥락을 구분하고 명확한 구조를 제공하는 접근을 설명한다. 원하는 출력과 동작을 테스트로 확인하는 것이 중요하다. [OpenAI 공식 prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)

여기서부터는 대회 배점과 무관한 자체 작업 틀이다. 요청을 읽으면 먼저 다음 여섯 줄을 적는다.

1. **목적:** 누구의 어떤 결정을 도울 것인가.
2. **입력:** 어떤 데이터·문서·로그가 제공됐는가.
3. **제약:** 시간, 사용 가능한 도구, 개인정보, 출력 길이는 무엇인가.
4. **성공 기준:** 어떤 수치·조건·동작이면 완료인가.
5. **검증:** 정답이나 성공 여부를 어떻게 독립적으로 확인할 것인가.
6. **불명확함:** 답에 영향을 주는 가정과 추가로 필요한 정보는 무엇인가.

이 틀을 모두 장문으로 모델에 보낼 필요는 없다. 제한된 AI 대화에서는 확인에 필요한 부분을 짧고 구체적으로 전달한다. 다음은 자체 연습용 요청 예시다.

> 아래 데이터에서 lot별 수율을 계산하라. 수율은 양품 chip 수/검사한 chip 수다. NULL 측정값은 정상으로 간주하지 않는다. 반환은 lot_id, 분자, 분모, 수율, 제외 행 수로 하라. 분모가 0이면 수율은 확인 불가로 적어라. 먼저 중복 키와 누락을 확인하고, 계산 후 L01의 결과를 수작업 집계와 대조하라.

여기서 강한 부분은 “전문가처럼 정확히”라는 표현이 아니라 분모 정의, NULL 처리, 출력 조건, 독립 확인이다. 같은 습관을 주문 API 오류 분석에도 적용한다. 입력 요청, 실제 응답, 기대 응답, 오류 로그, 관련 코드 범위를 제시하고 원인을 주장할 때 확인 방법을 함께 적도록 한다.

AI가 제시한 설명을 검증할 때에는 “다시 생각해 줘”만 반복하지 않는다. 틀릴 수 있는 구체적 가정을 지정한다. 예컨대 “LEFT JOIN 후 WHERE 필터로 미매칭 주문이 사라지는지 확인하라”, “0건 조회와 DB 오류를 같은 예외로 처리했는지 확인하라”처럼 검증 범위를 좁힌다. 대화 기록에는 실제 실행·판단만 남긴다. 하지 않은 테스트를 완료했다고 적는 것은 설명의 신뢰성을 떨어뜨린다.

## RAG를 준비하는 깊이와 실습 범위

RAG는 검색한 외부 자료와 언어 생성 모델을 결합하는 접근이다. 모델 파라미터의 지식만 사용했을 때의 한계를 외부 근거로 보완한다. 원 논문의 학습 구조와 오늘날 검색 문서를 프롬프트에 넣는 일반 구현은 세부 방식이 다를 수 있지만, 외부 근거 활용이라는 핵심 연결을 이해하는 데 유용하다. [Retrieval-Augmented Generation 원 논문](https://arxiv.org/abs/2005.11401)

1차 대비에서는 벡터 데이터베이스를 운영하기보다 다음 네 단계의 오류 위치를 설명하는 수준이면 충분하다.

- **입력 정리:** PDF·표·로그를 읽을 때 숫자·헤더·문서 ID가 보존되는가.
- **검색:** 정답 근거가 검색 후보에 포함되는가.
- **생성:** 제공된 근거만으로 주장과 수치를 만드는가.
- **검증:** 인용된 문서가 실제 주장에 연결되고 현행 자료인가.

“검색은 잘됐지만 답이 틀린 경우”와 “정답 근거가 처음부터 검색되지 않은 경우”는 수정 지점이 다르다. 자체 연습에서는 검색 문서 세 개를 사람이 직접 골라도 된다. 유료 API, embedding 다운로드, 서비스 배포가 있어야만 이러한 개념을 연습할 수 있는 것은 아니다.

버전·날짜·부서·권한을 메타데이터로 남기면 검색 대상을 좁힐 수 있다. 공식 retrieval 문서도 속성 필터를 설명한다. 다만 API를 그대로 설치하는 것이 목표는 아니다. [OpenAI 공식 retrieval](https://developers.openai.com/api/docs/guides/retrieval)

반도체 맥락의 자체 예시는 “장비 A의 경보 E12가 발생했을 때 현행 점검 순서”다. 현행 절차, 과거 절차, 유사한 다른 장비의 절차를 일부러 섞고 왜 다른 문서를 제외했는지 적는다. 답변에 인용 표기가 붙어 있어도 숫자와 조치가 문서에 실제 존재하는지 확인한다. 합당한 근거가 없으면 추가로 필요한 로그나 문서가 무엇인지 설명한다.

## 평가 지표와 데이터 누설

precision은 불량으로 예측한 것 중 실제 불량의 비율이고, recall은 실제 불량 중 잡아낸 비율이다. 불량이 드물면 모두 정상이라고 해도 accuracy가 높을 수 있다. 어떤 오류가 업무에 더 큰 비용을 만드는지와 함께 지표를 해석한다. [scikit-learn 공식 평가 지표](https://scikit-learn.org/stable/modules/model_evaluation.html)

자체 계산 연습은 실제 불량 20개, 그중 탐지 15개, 정상 오탐 10개로 시작한다. TP=15, FN=5, FP=10이며 precision은 15/25, recall은 15/20이다. 그 뒤 “불량 누락을 줄이고 싶다”와 “정상 제품을 과도하게 격리하면 비용이 크다”라는 두 목적을 비교한다. 같은 모델 수치도 목적에 따라 다르게 평가해야 한다.

데이터 누설은 실제 예측 시 사용할 수 없는 정보를 모델 개발에 쓰는 문제다. 분할 전에 전체 데이터로 전처리를 학습하면 테스트 정보가 들어갈 수 있다. [scikit-learn 공식 공통 실수 문서](https://scikit-learn.org/stable/common_pitfalls.html)

같은 wafer·lot에서 나온 행이 양쪽에 섞이는 문제와 시간에 따른 변화도 점검한다. 처음 보는 wafer나 미래 생산을 목표로 하면 해당 일반화 조건에 맞는 그룹·시간 분할이 필요하다. [scikit-learn 공식 교차검증](https://scikit-learn.org/stable/modules/cross_validation.html)

LLM 응용에서는 정답 질문을 보고 프롬프트를 반복 수정하는 행위도 평가셋에 대한 적응이 될 수 있다. 개발용 예시와 최종 확인용 예시를 구분한다. AI judge를 쓰더라도 명확한 기준과 사람 판정으로 점검하고, 순서·길이·문체 때문에 점수가 달라지는지 확인한다. [OpenAI 공식 evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

현재 준비에는 별도 평가 플랫폼 계정이나 새 유료 서비스를 만들기보다 작은 표로 결과를 남기는 편이 간단하다. 각 사례의 기대 결과, 실제 결과, 오류 유형, 수정 내용, 재확인 결과를 한 행씩 기록하면 된다. “그럴듯하게 보인다”는 평가는 숫자·실행 결과·근거 연결을 대신할 수 없다.

## 웹 개발 경험을 바로 활용하는 데이터 코드 확인

### SQL과 표의 기본 함정

SQLite의 COUNT(*)는 행 수이며 COUNT(value)는 value가 NULL이 아닌 행을 센다. 두 정수의 나눗셈은 소수점이 잘릴 수 있다. [SQLite 집계 함수](https://www.sqlite.org/lang_aggfunc.html), [SQLite 표현식](https://www.sqlite.org/lang_expr.html)

JOIN은 분석 단위도 바꿀 수 있다. 일대다 관계라면 생산 수량이 이벤트 수만큼 반복되고, 중복 키가 양쪽에 있으면 결과 행 수가 크게 늘어난다. LEFT JOIN 후 오른쪽 열의 WHERE 조건은 NULL로 보충된 미매칭 행을 제거할 수 있다. [pandas 공식 병합 문서](https://pandas.pydata.org/docs/user_guide/merging.html), [SQLite SELECT](https://www.sqlite.org/lang_select.html)

자체 연습 체크 순서는 행 수, 고유 ID 수, NULL 수, JOIN 전후 수량 합계, 집계 단위, 분모 정의다. A lot의 수율이 9/10이고 B lot이 50/100이면 chip 전체 기준은 59/110이다. 두 비율의 평균 70%는 lot을 동일 가중치로 취급한 다른 계산이다. 어느 값이 맞는지는 요청한 지표의 정의로 결정한다.

SQL을 AI가 만들었으면 우선 작은 데이터에서 수작업 결과와 대조한다. 조회 0건, 중복 키, 경계 날짜, NULL, 범위 밖 수치를 포함한다. 오류가 없는 실행은 의미가 올바른 실행의 증거가 아니다. DB 방언도 명시한다. SQLite에서 통과한 쿼리가 모든 DB에서 같은 의미·문법으로 동작한다고 판단하지 않는다.

사용자 값을 SQL 문자열에 직접 끼워 넣는 대신 매개변수로 바인딩한다. [Python sqlite3 공식 문서](https://docs.python.org/3/library/sqlite3.html)

### JSON을 세 층으로 검사하기

JSON 파싱은 문법, 스키마 검사는 필드·타입·허용 값, 업무 검사는 수치·단위·근거의 의미를 확인한다. 구조화 출력도 의미적 실수를 포함할 수 있고 거부·불완전 응답 처리도 필요하다. [Python JSON](https://docs.python.org/3/library/json.html), [OpenAI 공식 structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

자체 연습은 “수율이 문자열”, “필수 lot_id 없음”, “수율 135%”, “분모 0인데 정상 수율”, “출처에 없는 장비 ID”를 순서대로 검사하는 것이다. 각 오류를 어떤 층에서 잡아야 하는지 적는다. 숫자 타입이라는 이유만으로 계산을 승인하지 않으면 된다. 웹 개발에서 쓰던 API 계약 검증을 AI 응답에도 그대로 적용할 수 있다.

### 코드 읽기와 검증

작은 기능의 검증에는 독립적인 기대값, 경계 입력, 예외 경로가 중요하다. Python의 기본 unittest만으로도 기대값 비교와 예외 확인을 할 수 있다. [Python unittest 공식 문서](https://docs.python.org/3/library/unittest.html)

자체 API 오류 분석 연습에서는 인증 실패, 존재하지 않는 ID, 빈 조회, DB timeout, 중복 주문, 문자열 숫자 변환을 나눠 본다. 반환 상태와 본문이 기대 계약에 맞는지 확인한다. 실제로 수행한 확인과 아직 수행하지 못한 확인을 구분해서 설명한다. 테스트 기대값을 구현식 그대로 복사해서 만들면 같은 오류를 함께 재현할 수 있으므로, 숫자 하나는 사람이 먼저 계산해 둔다.

## 도구 호출 에이전트 보안

도구 호출은 모델이 함수 이름과 인수를 내보내는 단계와 애플리케이션이 실제 함수를 실행하는 단계가 다르다. 반환 결과를 다시 모델에 전달하고 최종 응답을 생성할 수도 있다. [OpenAI 공식 function calling](https://developers.openai.com/api/docs/guides/function-calling)

ReAct 원 연구는 reasoning과 action을 함께 다루며 외부 정보와 상호작용하는 접근을 설명한다. 이 문서를 근거로 모든 과제에서 다중 에이전트가 필요하다고 결론 내릴 수는 없다. [ReAct 원 논문](https://arxiv.org/abs/2210.03629)

자체 설계 연습은 작업 한 개에 도구 두 개로 시작한다. 모델은 계획이나 선택을 하고, 코드가 타입·범위·허용 작업·시간 예산·실제 실행을 관리한다. 같은 호출을 반복하면 재시도 이유를 분류하고 종료 조건을 둔다. 단일 흐름에서 검증 가능한 결과가 나온 뒤 역할 분리가 실제 시간이나 정확도를 개선하는지 비교한다.

외부 문서에 들어 있는 명령을 신뢰된 작업 지시처럼 처리하면 간접 prompt injection이 발생할 수 있다. RAG나 fine-tuning만으로 이 문제를 완전히 해결하지 못한다. [OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

필요 이상으로 도구 기능·권한·자율성을 제공하는 것도 위험하다. 읽기 목적의 요약 도구에 삭제·전송·설정 변경 기능까지 줄 이유는 없다. [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

자체 상황 문제에서는 “문서를 읽어 원인 후보를 정리하라”와 “장비 설정을 바꾸라”의 권한 차이를 설명한다. 모델에게 비밀을 말하지 말라는 지시만 주는 것보다 비밀을 입력 밖에서 관리하고, 서버가 허용된 기능만 수행하게 한다. 정책 문서에 수상한 명령이 있으면 해당 문구가 업무 근거인지 동작 변경 요구인지 분류한다. 이는 응시 감독을 회피하거나 실제 장비에 접근하는 실습이 아니라 로컬 합성 자료로 개념을 익히는 연습이다.

## Cofa Probe의 공개 철학과 이후 단계 준비

공식 Probe 안내는 산출물만이 아니라 프롬프트·도구 설정·AI 대화·검증 기록과 사후 Q&A를 함께 본다고 설명한다. 평가 축은 기술, 의도, 인지다. 기술은 작동·구조·보안, 의도는 목표·분해·검증, 인지는 결과의 원리·한계에 대한 이해와 연결된다. 국문 안내는 과제별 감독 조건에 따라 카메라·세션 기록 등을 확인하며 실제 응시 환경의 안내가 적용된다고 명시한다. **이는 플랫폼 일반 안내이며 SK 대회별 시간·제공 모델·허용 도구의 확정 규칙은 아니다.** [Probe 공식 안내](https://www.getcofa.com/ko/probe), [Probe 영문 설명](https://www.getcofa.com/en/probe)

과거 크래프톤·올리브영 Cofathon 공식 사이트는 현업 문제를 정의하고 작동하는 결과물을 만드는 트랙을 소개한다. 다른 행사 사례이므로 SK하이닉스에서 동일 과제나 같은 규칙을 쓴다고 추정하지 않는다. [Cofathon 공식 사이트](https://cofathon.getcofa.com/)

이후 단계에 대비한 자체 권고는 “결과물의 중요한 부분을 직접 설명할 수 있을 만큼 작게 만들기”다. 예를 들어 문서 검색 앱이라면 문서 수집, 검색, 근거 생성, 인용 확인의 데이터 흐름을 설명하고 한 가지 실패 사례를 재현한다. 생산 데이터 앱이라면 행 수가 바뀌는 구간과 비율의 분모를 말할 수 있어야 한다. API 과제라면 오류 발생 조건과 응답 계약을 설명한다.

면접 또는 사후 설명 연습은 다음 질문을 스스로 답하는 것으로 시작한다. 왜 이 방법을 골랐는가. 더 단순한 방법은 무엇인가. 어떤 입력에서 깨지는가. 실제로 실행한 검증은 무엇인가. 코드나 문서의 어느 부분이 근거인가. 시간이 더 있었다면 무엇을 먼저 고칠 것인가. 이 질문 목록은 공식 문제 복원이 아니라 자신의 결과물을 이해하기 위한 연습이다.

AI를 쓸 수 있는 사전 연습에서는 첫 답을 받아 적은 뒤 검증해서 고치는 과정을 경험한다. 마지막에는 AI 없이 오류를 설명할 수 있는지 확인한다. 실제 시험에서 도구 사용이 허용되는지는 별도 안내를 따르고, 연습 환경의 사용 권한을 그대로 가정하지 않는다.

각 실습은 비공식 10점 기준으로 평가할 수 있다. 문제·분모·조건 정의 2점, 결과의 정확성 3점, 독립 검증 3점, 오류·한계 설명 2점이다. 일반 입력 한 개만 맞추면 10점을 주지 않는다. 총점은 자신의 학습 균형을 보기 위한 것이고 대회 합격선과 비교하지 않는다. 질문 횟수나 도구 수를 줄인 것만으로 가산점을 주지도 않는다.

실패하면 기능을 추가하기 전에 실패 원인을 한 종류로 분류한다. 입력 이해, 논리·계산, 검색 누락, 근거 충돌, 구현, 권한, 검증 누락 중 어디인지 적고 그 지점만 수정한다. 수정 후에는 이전에 실패한 동일 사례를 다시 확인한다. 새로운 예쁜 화면이 생겼다는 사실은 이전 계산 오류가 해결됐다는 증거가 아니다.
