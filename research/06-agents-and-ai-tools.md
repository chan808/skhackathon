# 에이전트와 AI 도구를 이해하고 준비하기

기준일 2026년 10월 14일 한국시간. 제품 기능과 공개 문서는 이 날짜에 확인했다. SK하이닉스 실전의 외부 AI 도구 허용 여부는 별도의 대회 안내를 따른다.

**Claude Code와 Codex는 이미 에이전트다. ChatGPT 앱에도 도구와 다단계 작업 기능이 있으므로, 에이전트를 쓰려면 반드시 새로운 프로그램을 만들어야 하는 것은 아니다.** 직접 개발할 때의 추가 가치는 원하는 업무의 데이터, 실행 도구, 권한, 저장 상태, 검증 기준과 사용자 화면을 자신이 설계하는 데 있다.

## 모델 앱 에이전트를 구분하기

모델은 입력 문맥을 받아 텍스트나 도구 호출 요청을 생성하는 구성 요소다. 앱은 사용자 화면과 실행 환경이다. 에이전트는 그 안에서 목표와 관찰 결과에 따라 다음 행동을 선택하며 작업하는 방식이다. 세 용어는 서로 같은 층위의 제품 분류가 아니다.

이 문서에서는 다음과 같은 실행 구조를 에이전트의 핵심으로 본다.

1. 목표와 현재 자료를 읽는다.
2. 모델이 다음에 사용할 도구와 인수를 선택한다.
3. 실행 환경이 권한과 입력을 검사하고 도구를 실행한다.
4. 파일 내용, 계산 결과, 오류 등 실제 관찰을 모델에 돌려준다.
5. 모델이 추가 작업, 수정, 종료 또는 사람의 판단이 필요한지 결정한다.

OpenAI Agents SDK의 공식 실행 문서도 모델 호출, 도구 실행, 관찰 반영, 최종 종료 또는 다른 에이전트로의 인계를 설명한다. 이 반복을 runner가 관리한다. [OpenAI 공식 agent loop](https://developers.openai.com/api/docs/guides/agents/running-agents)

다만 에이전트라는 단어의 정의는 문헌과 제품마다 다르다. Anthropic은 미리 정해진 코드 경로를 따르는 workflow와 모델이 동적으로 경로·도구 사용을 정하는 agent를 구분한다. 이 구분을 쓰면 “LLM이 들어갔으니 전부 자율 에이전트”라는 혼동을 줄일 수 있다. [Anthropic 공식 설명](https://www.anthropic.com/engineering/building-effective-agents)

**workflow가 언제나 결정적이라는 뜻은 아니다.** 고정된 순서에서 LLM을 호출하면 순서는 고정돼도 생성 결과는 달라질 수 있다. 반대로 LLM 없이 정해진 규칙과 계산만 수행하는 프로그램은 이 문서에서 결정적 workflow라고 부른다. 반복문, 분기, 로그가 있다는 사실만으로 모델이 다음 행동을 선택하는 에이전트가 되지는 않는다.

## ChatGPT 앱과 Claude Code는 어디가 다른가

Claude Code 공식 문서는 맥락 수집, 행동, 결과 검증을 반복하는 구조를 명시한다. 파일 검색·수정·명령 실행 등의 도구 결과가 다음 판단에 반영된다. Claude Code는 모델을 둘러싼 실행 도구와 문맥 관리 계층인 harness를 제공한다. [Claude Code 작동 원리](https://code.claude.com/docs/en/how-claude-code-works)

Codex도 로컬 프로젝트를 읽고 수정하고 명령·검증을 실행하는 개발용 경험이다. 사용자는 진행 중 방향을 수정하고 결과의 차이와 실행을 검토할 수 있다. [Codex CLI 공식 문서](https://learn.chatgpt.com/docs/cli)

ChatGPT의 현재 공식 문서는 대화 중심의 Chat, 결과물까지 수행하는 Work, 개발 도구를 사용하는 Codex를 구분한다. Chat에서도 검색 등 도구를 사용할 수 있고, Work는 계획·맥락 수집·도구 실행을 거쳐 결과물을 만들 수 있다. 따라서 “ChatGPT는 말만 하고 Claude Code만 행동한다”는 설명은 정확하지 않다. [ChatGPT 공식 사용 안내](https://learn.chatgpt.com/docs/use-chatgpt)

실제로 쓸 수 있는 파일·브라우저·연결 서비스는 제품 이름만으로 확정되지 않는다. 계정, 실행 위치, 연결된 도구와 권한 설정에 따라 다르다. 아래 비교는 작업 방식과 개발 책임의 비교이며 모든 계정에 같은 기능이 열린다는 뜻이 아니다. [ChatGPT Work 공식 실행 안내](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-overview)

| 사용 방식 | 다음 단계 선택 | 실행 대상 | 내가 주로 맡는 일 |
|---|---|---|---|
| ChatGPT에서 대화 중심으로 사용 | 사용자가 후속 요청을 주고, 가능한 도구는 모델이 선택할 수 있음 | 첨부 자료와 승인된 도구 | 자료 제공, 질문, 답 검토 |
| ChatGPT Work 같은 다단계 작업 경험 | 모델이 계획하고 관찰에 따라 진행 | 기능·권한이 허용한 파일과 도구 | 목표·제약 전달, 진행 방향과 산출물 검토 |
| Claude Code 또는 Codex | 모델이 파일 읽기·수정·명령·검증을 반복 | 주어진 작업 환경과 승인된 연결 | 요구사항, 코드·실행 증거, 접근 범위 관리 |
| 직접 만든 고정 workflow | 프로그램에 정한 경로 | 좁게 정의한 함수와 자료 | 입력 계약, 계산·검증·예외 경로 설계 |
| 직접 만든 에이전트 앱 | 모델이 허용된 도구 중 선택하고 반복 | 앱이 노출한 업무별 도구 | 도구·권한·상태·종료·평가·화면 설계 |

대화창 모양도 판단 기준이 아니다. 같은 채팅 UI 뒤에 단일 모델 호출, 고정 workflow, 에이전트 loop 중 무엇이든 구현할 수 있다. 중요한 차이는 어느 단계의 결정을 사람이 내리고, 어느 단계는 코드로 고정하며, 어느 단계는 모델에 맡기는가다.

## 기존 에이전트를 쓰는 것과 내 앱을 만드는 것

기존 도구를 쓸 때에는 Claude Code나 Codex가 실행 loop, 파일·터미널 도구, 문맥 관리 등의 공통 부분을 제공한다. 내가 할 일은 목표, 제공 자료, 완료 조건과 검증을 명확히 하는 것이다.

내 앱을 만들면 동일한 모델을 써도 환경을 업무에 맞게 좁힐 수 있다. 예를 들어 “전체 터미널을 사용할 수 있는 분석 도우미” 대신 “이 사용자가 접근할 수 있는 lot만 조회하고, 지정한 수율 정의로 계산하며, 근거가 있는 점검 후보만 반환하는 서비스”를 제공할 수 있다. 이 부분은 스스로 설계한 예시이며 SK 실제 문제를 예측한 것이 아니다.

| 앱 개발자가 정할 부분 | 생산 데이터 분석 예시 |
|---|---|
| 사용자의 목적과 화면 | lot ID 선택, 원인 후보와 근거를 확인하는 화면 |
| 데이터 접근 | 사용자별 허용 lot와 읽기 전용 조회 |
| 도구 계약 | 조회·집계·문서 검색·결과 검증 함수의 입력과 출력 |
| 업무 규칙 | chip 기준 수율, 누락값, 중복, 버전·효력 기간 |
| 상태 | 어떤 자료로 어떤 검증을 했는지와 미완료 작업 |
| 반복의 경계 | 최대 단계·시간·실패 횟수, 중단 또는 추가 자료 요청 |
| 결과 검증 | 수치 일치, 문서 근거, 출력 형식, 허용 범위 |
| 운영 기록 | 모델 요청·도구 결과·실패·승인·최종 산출물의 연결 |

OpenAI 공식 안내는 SDK를 쓰면 앱이 배포·도구·저장소·승인 등을 소유하고 runner가 실행 loop를 맡는 구조를 설명한다. 모델 API를 직접 호출하며 loop를 구현하는 방법도 있다. SDK는 이러한 반복 관리의 편의 수단이지, 모든 실습 전에 설치해야 하는 필수 구성 요소는 아니다. [OpenAI 공식 런타임 비교](https://developers.openai.com/api/docs/guides/agents)

개발자가 무엇을 만들지에 따라 기존 Codex harness를 앱에 포함하는 방법도 존재한다. 공식 문서는 공통 실행 계층과 제품의 업무 맥락·도구·화면을 분리한다. 지금 준비를 위해 이를 바로 도입할 필요는 없지만, “직접 앱을 만든다”가 “agent loop를 모두 처음부터 재작성한다”만 뜻하는 것은 아니다. [Codex harness 공식 설명](https://developers.openai.com/blog/codex-as-a-platform)

## 같은 CSV와 점검 문서를 네 가지 방식으로 처리하면

다음은 자체 학습 시나리오다. 두 파일을 받았다고 가정한다.

- CSV에는 lot별 chip 검사 결과, 누락값과 중복된 기록이 있다.
- SOP에는 장비별 현행 점검 순서와 오래된 버전이 함께 있다.
- 요청은 “수율이 낮은 lot를 찾고 문서에 근거한 점검 후보를 설명하라”다.
- 완료 조건은 수치 검증, 현행 문서 인용, 확정 원인과 가설의 구분이다.

### ChatGPT 앱에서 수행

파일을 올리고 지표 정의와 원하는 결과를 요청한다. 파일 분석이나 코드 실행 도구가 제공되면 해당 도구로 집계할 수 있다. 결과가 나오면 분모·누락·중복을 확인하고 SOP의 주장과 인용을 대조한다. 다단계 작업 기능이 있다면 반복 검증을 맡길 수도 있다. 사용자가 매 단계 계산 결과를 옮겨 주며 진행한다면 사용자가 작업 흐름을 조정하는 비중이 커진다.

앱이 에이전트 기능을 지원하는지와 별개로, “표를 읽을 수 있다”는 사실만으로 해당 계정이 이 PC의 폴더나 회사 DB에 직접 접근한다고 판단하지 않는다.

### Claude Code 또는 Codex로 수행

합성 CSV와 SOP를 프로젝트에 두고 읽기·분석·검증을 요청한다. 도구가 파일을 읽고 코드를 실행하면 실패 원인을 보고 수정할 수 있다. 작업 후에는 실제 생성 파일, 계산 명령, 검증 결과를 확인한다. 코딩 에이전트의 장점은 로컬 코드와 반복 검증을 같은 작업 안에서 다루기 쉽다는 것이다. 내가 수율 정의를 잘못 주면 도구가 많아도 잘못된 목표를 정확히 구현할 수 있다.

### 고정된 프로그램으로 수행

입력 형식 검사, 중복 처리, 수율 계산, 버전 필터, 정해진 출력 검증을 코드에 고정한다. 허용한 형식만 다루고, 처리할 수 없는 입력은 명시적으로 실패시킨다. 이 과제가 이미 명확히 정의됐다면 이 방법이 충분할 수 있다. 새로운 원인 조사 경로를 자유롭게 고르는 기능은 없지만 계산과 반복 실행의 기준선으로 유용하다.

고정 프로그램의 출력을 LLM이 설명하게 추가할 수도 있다. 이 경우에도 다음 조사 경로가 코드에 고정돼 있다면 전체 구조를 자율 에이전트로 부를 필요는 없다.

### 업무 전용 에이전트 앱으로 수행

앱은 read_lot, calculate_yield, search_current_sop, verify_claims처럼 목적이 좁은 도구를 제공한다. 모델은 CSV 문제를 보고 추가 검증이 필요한지, 어떤 현행 문서를 찾아야 하는지 판단한다. 코드가 lot 권한, 인수, 버전 필터와 반복 한도를 관리한다. 검증이 실패하면 모델은 요청을 수정하거나 불충분한 근거를 보고하고 종료한다.

이 방식의 추가 작업은 웹 화면만 만드는 일이 아니다. 도구를 어떤 조건에서 실행하고, 상태를 무엇으로 저장하고, 어떤 실패를 허용하며, 결과의 타당성을 무엇으로 판단할지 결정해야 한다. SOP상 연관된 점검 항목을 찾은 것만으로 물리적 결함 원인을 입증했다고 말하지 않는다.

## MCP skill RAG subagent orchestration의 역할

| 용어 | 무엇을 제공하나 | 위 시나리오의 예 | 혼동하면 안 되는 점 |
|---|---|---|---|
| Tool | 실행 가능한 기능과 계약 | 특정 lot의 검사 기록 조회 | 도구 호출 요청과 실제 실행은 다름 |
| MCP | 도구·데이터를 AI 앱에 연결하는 표준 인터페이스 | 사내 문서 검색 기능을 여러 클라이언트에 연결 | MCP 서버 연결 자체가 agent loop는 아님 |
| Skill | 재사용할 작업 지침과 보조 자료·스크립트 | 수율 분석 시 지켜야 할 단계와 검증법 | 지침을 추가했다고 DB 접근 권한이 생기지 않음 |
| RAG | 검색한 근거를 생성에 활용 | 현행 SOP를 찾아 답변에 제공 | 단일 답변에도 쓸 수 있으며 다중 에이전트는 필수 아님 |
| Subagent | 별도 문맥과 역할로 수행하는 작업자 | 데이터 검증과 문서 확인을 분업 | 역할 이름을 프롬프트에 세 개 쓰는 것과 실제 별도 실행은 다름 |
| Orchestration | 실행 순서·분업·상태·종료를 관리 | 검증 결과를 받고 다음 도구나 담당자를 선택 | 고정 코드로도, 모델 판단으로도 조정 가능 |
| Guardrail | 입력·출력·도구 실행을 검사하는 경계 | 허용 lot 범위와 숫자·인용 확인 | “실수하지 마”라는 지시만으로 모든 검사 대체 불가 |

MCP 공식 설명은 AI 앱과 외부 시스템의 도구·데이터 연결을 다룬다. Claude Code도 MCP를 통해 DB·API 등에 연결할 수 있다고 안내한다. 새로운 연결은 실제 외부 시스템이 필요한 경우에 추가하면 된다. [MCP 공식 개요](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro), [Claude Code MCP 공식 안내](https://code.claude.com/docs/en/mcp)

Claude Code의 skill은 SKILL.md의 지침을 필요할 때 적용하며 자료와 스크립트를 함께 둘 수 있다. subagent는 자신의 문맥·지시·도구 접근을 가진 작업자로 결과를 전달한다. [Claude Code skills](https://code.claude.com/docs/en/skills), [Claude Code subagents](https://code.claude.com/docs/en/sub-agents)

OpenAI SDK는 전문가가 대화를 넘겨받는 handoff와, 주 에이전트가 전문가를 도구처럼 호출하고 최종 책임을 유지하는 방식을 구분한다. 모든 분업이 대화의 소유권 이전을 의미하지 않는다. [OpenAI orchestration 공식 문서](https://developers.openai.com/api/docs/guides/agents/orchestration)

RAG의 기본 개념은 외부 검색 근거와 생성을 결합하는 것이다. 특정 MCP 서버나 별도 worker가 있어야만 가능한 것은 아니다. [RAG 원 논문](https://arxiv.org/abs/2005.11401)

## 검증과 통제는 에이전트에 추가할 핵심 기능

모델이 “끝났다”고 말하는 것과 결과가 맞는 것은 다르다. 도구의 성공 상태, 숫자, 인용, 파일 생성 여부를 실제 자료로 확인한다. 이 프로젝트에서 익히려는 AI Native 역량도 에이전트 숫자보다 목표를 전달하고 오류를 발견·수정·설명하는 능력과 가깝다.

개발용 에이전트의 평가는 최종 문장뿐 아니라 어떤 도구를 호출했고, 관찰을 제대로 반영했으며, 불필요한 단계나 지시 위반이 있었는지 포함한다. 공식 문서는 trace로 모델·도구·분업의 경로를 보고 반복 평가할 것을 설명한다. [OpenAI agent evaluation](https://developers.openai.com/api/docs/guides/agent-evals), [SDK integrations and observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability)

입력·출력 검사와 민감한 도구 실행 전 검토는 구현 경계에 둔다. SDK의 guardrail이나 approval 기능을 사용하는 경우에도 어떤 단계에 적용되는지 확인해야 한다. [OpenAI guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)

Claude Code 역시 도구별 권한과 허용·거부 설정을 제공한다. 권한을 넓히는 것과 분석 정확도가 높아지는 것은 다른 문제다. [Claude Code permissions](https://code.claude.com/docs/en/permissions)

자체 실습에서는 실행 기록에 목표, 도구·인수, 결과, 검증, 다음 행동의 이유를 남긴다. 작은 JSON이나 텍스트 로그로 시작해도 된다. 테스트 5개가 모두 통과한 이유를 설명할 수 있으면, 검증 기준 없이 에이전트 5개를 호출하는 것보다 준비 상태를 판단하기 쉽다. 이 문장은 공식 배점이 아니라 이 프로젝트의 학습 권고다.

## 지금 필요한 셋업과 나중에 추가할 셋업

2026년 10월 14일 로컬 읽기 점검에서 PATH의 codex.exe와 claude.ps1을 찾았고, 버전은 Claude Code 2.1.177과 Codex CLI 0.162.0-alpha.17.2로 확인했다. **설치 엔트리가 있으므로 새 코딩 에이전트 설치부터 할 필요는 없다.** 이 점검만으로 로그인 상태, 현재 구독·기능, 모든 실행 권한 또는 대회 허용 여부가 확인된 것은 아니다.

1차 준비를 위해 우선 필요한 구성은 다음 정도다.

1. 합성 자료를 둘 폴더와, 정답·경계 사례를 비교할 계산 코드.
2. 익숙한 코딩 에이전트 하나에 전달할 목적·자료·완료·검증 조건.
3. 실제 읽기·실행·수정·재검증이 일어났는지 확인할 파일과 로그.
4. 외부 문서의 현행 버전과 근거를 대조하는 연습.
5. 실제 응시 안내의 허용 도구와 환경 확인.

이 단계에서 새로운 agent framework, 벡터 DB, 클라우드 배포, 여러 MCP 서버를 함께 설치해야 한다는 근거는 없다. Anthropic 공식 설계 글도 요구를 충족하는 간단한 해법부터 시작하고 복잡성의 이득을 확인하라고 권한다. [간단한 agent 설계의 공식 근거](https://www.anthropic.com/engineering/building-effective-agents)

이후 실제 과제가 주어졌을 때 선택은 다음 기준으로 결정한다.

| 요구 | 시작할 방법 |
|---|---|
| 한 번의 설명·자료 이해 | 기존 ChatGPT 또는 Claude 대화와 필요한 도구 |
| 명확한 집계·규칙 검증 | 고정된 코드 |
| 로컬 파일을 읽고 코드·테스트를 반복 수정 | 기존 Claude Code 또는 Codex |
| 반복되는 분석 절차를 기존 도구에서 재사용 | 작업 지침 또는 작은 skill |
| 외부 DB·문서 서비스의 기능 연결 | 직접 함수나 적절한 MCP 연결 |
| 일반 사용자가 반복 이용할 업무 서비스 | 앱의 UI·도구 계약·권한·평가부터 설계 |
| 입력마다 조사 경로·도구가 달라져 고정 순서가 부족 | 좁은 도구를 가진 단일 에이전트 |
| 독립된 전문 작업·문맥이 실제로 필요 | 분업의 비용과 효과를 확인한 뒤 subagent |

현재는 에이전트의 기본 loop를 이해하고, 이미 가진 도구로 실제 오류를 발견·수정·검증하는 연습이 우선이다. 직접 만든 규칙 기반 데모는 모델을 부르지 않는다면 그 사실을 명시해야 한다. 그러한 데모는 도구 계약·관찰·검증·중단을 배우는 기준선이며, 실제 LLM이 다음 행동을 선택하는 에이전트의 성능을 측정한 결과가 아니다.
