# 프로그래머스 사전 체험과 SK하이닉스 예선 준비 분석

2026년 10월 15일 앞선 분석에서 로그인된 [공식 체험](https://programmers.co.kr/ai-assessment/preview)의 **6개 유형·24개 문항을 읽었다고 기록한 자료**다. 자료 전체의 정답표를 복원하거나 실제 시험을 응시한 것은 아니다. 지식과 간식의 독립 풀이·계산, 구독·규정·전문 사례의 핵심 자료 대조 범위는 아래에 표시했다. 앞선 기록에는 AI 질문 횟수와 답안 제출을 사용하지 않았다고 명시돼 있다. 아래 선택과 계산은 공식 채점 결과가 아니다.

**이번 재점검은 공개 목록·FAQ와 프로젝트 파일을 확인했으나 로그인 후 전체 원자료를 새로 대조하지 못했다.** 산술 일관성을 재확인한 것과 원자료의 정확성을 확인한 것을 구분한다. [재점검 상태와 완료 기준](#재점검-상태와-전체-자료-완료-기준)을 함께 읽는다.

**준비의 중심은 AI 개념을 상황에 적용하고, 제한된 AI로 여러 자료를 구조화·검산하는 능력이다.** ‘낮은 수준의 AI와 간단한 지식만 있으면 충분하다’는 표현은 지식 문항에는 일부 맞지만, 수십 개 파일의 조건 판정과 전문 보고서까지 설명하지 못한다. 미리보기는 여러 기업의 공통 체험이며 SK 전용 모의시험이라는 근거는 없다. [SK 공식 일정](https://skhynix-hackathon.com/ai-2026), [플랫폼 공식 설명](https://programmers.co.kr/ai-assessment/insight/why-we-built-ai-assessment)

FAQ에 따르면 체험은 PC용이며 시간 제한·화상 감독·별도 결과 리포트가 없다. 체험은 반복 가능하나 AI 대화 사용 횟수는 초기화할 수 없고 제한은 10회로 안내한다. 모델 응답 품질도 실전과 다를 수 있다. 화면에서 첨부 파일 20,000토큰 한도를 확인했다. **이는 첨부 선택 한도이지 모델의 전체 컨텍스트 길이 아니다.** 활용 예제의 AI 패널은 1-4번 문제를 함께 가리키므로 각 소문항에 10회씩 있다고 확정하지 않는다.

제품 설명은 질문 제한·30초 대기·지문 복사 제한과 과정·결과 평가를 소개한다. 이는 플랫폼 설명이며 SK 실제 설정은 개인 초대가 우선한다. 베타 사례의 점수 차이를 SK 채점 가중치로 역산하지 않는다. [공식 설명](https://programmers.co.kr/ai-assessment/insight/why-we-built-ai-assessment)

## 지식 10문항의 독립 풀이

문제와 보기를 다시 쓰지 않고 판단 근거를 정리한다. 1-5번은 4지선다, 6·10번은 O/X다.

| 번호 | 선택 | 판단 근거와 함정 |
| --- | --- | --- |
| 1 | 1번 | 텍스트 생성의 확률적 예측 설명이 적절하다. 엄밀한 생성 단위는 단어보다 토큰이다. 이미지 생성이 사실성을 보장하는 복사·조합이라는 설명은 틀리다 |
| 2 | 1번 | 언어 기반 요약과 텍스트 조건 이미지 생성을 구분한다. 서로 다른 모달리티도 같은 플랫폼에서 제공 가능하다 |
| 3 | 3번 | 데이터 분석 전문가 역할, 설비의 최근 일주일 평균으로 결측 대체, 최종 표 출력의 세 조건을 모두 충족한다. 역할·규칙·형식 중 하나만 어겨도 제외 |
| 4 | 2번 | 직무의 행동·상황 대응 능력을 평가한다. 문화적 배경이나 연령·국적별로 다른 질문을 만드는 것이 자동으로 공정해지지는 않는다 |
| 5 | 3번 | 제시된 보기 중 분포·언어 구조를 고려한 합성 데이터가 목적과 일정의 대안이다. 이름 마스킹이나 사내 서버 사용만으로 동의 요구가 사라진다고 볼 수 없다 |
| 6 | X | 도구의 상업적 이용 허용과 생성 로고의 제3자 저작권·상표 침해 검토는 별개다 |
| 7 | 1번 | 검색 결과의 날짜·버전 메타데이터와 우선순위를 개선한다. 오래된 문서도 벡터 유사도는 높을 수 있어 임계치 상향만으로 시점 혼용을 해결하지 못한다 |
| 8 | 1번 | 외부 필드와 템플릿 변수의 매핑 누락이 확인된 원인이다. 근거 없는 토큰 초과·API 지연·임베딩 문제로 바꾸지 않는다 |
| 9 | 1번 | 예측 후 설명 모델로 지표 기여도를 추출하여 시각화하는 파이프라인이 요구와 맞는다. 자연어 설명이 실제 모델의 판단 근거를 자동으로 증명하지 않는다 |
| 10 | X | 가명 처리를 했다는 이유만으로 삭제 권리 대응·위험 통제·보존 관리를 모두 면제하고 무기한 사용할 수 있다는 판단은 부적절하다 |

3번의 평균 대체는 **문항에서 요구한 규칙**이다. 현실의 결측치는 누락 원인·시간 누출·분포·불확실성을 확인하여 대체법을 정해야 한다. 5번에서도 합성 데이터는 자동으로 안전하거나 원자료와 동등한 성능을 보장하지 않는다. 원자료의 적법한 사용, 재식별·원문 재현, 분포와 모델 성능을 검증해야 한다. 가명 처리와 익명 처리는 구분한다. [ICO의 가명 처리 설명](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-sharing/anonymisation/pseudonymisation)

보기 풀이에는 ‘문제의 필수 조건 목록 만들기 → 각 보기의 조건 누락 찾기 → 확인된 원인을 직접 해결하는 보기 선택’이 효과적이다. 실제 샘플에는 역전파·행렬 미분·CNN 출력 크기 계산이 없었으나 이것이 실제 출제 범위에서 제외된다는 의미는 아니다.

## 간식 설문 4문항

PDF 신청 50건과 이미지 명부 17명을 대조했다. 동일인이 여러 번 신청하면 **시간상 마지막 한 건만 유효**하다. 같은 메뉴를 반복해도 이전 기록은 취소된다.

| 문항 | 독립 계산 결과 | 보기 |
| --- | --- | --- |
| 1 | 첫 문항 대상 학생의 마지막 신청은 컵라면 | 4번 |
| 2 | 경영학과의 최종 토스트 신청자는 1명 | 1번 |
| 3 | 가장 많이 취소된 메뉴는 토스트 | 5번 |
| 4 | 미신청자는 전자공학과 26학번 1명 | 4번 |

| 메뉴 | 원래 기록 | 최종 유효 | 취소 |
| --- | ---: | ---: | ---: |
| 떡볶이 | 11 | 4 | 7 |
| 부리또 | 8 | 1 | 7 |
| 햄버거 | 12 | 6 | 6 |
| 토스트 | 13 | 3 | 10 |
| 컵라면 | 6 | 2 | 4 |
| 합계 | 50 | 16 | 34 |

검산은 `50 = 16 + 34`, `17명 - 신청자 16명 = 미신청 1명`이다. 최종 메뉴가 바뀐 사람 수와 취소된 **기록 수**는 다르다. PDF의 좌·우 표를 시간 순으로 결합하고, 이름·학과·학번을 연결한 뒤 마지막 기록을 선택한다. 명부와 신청을 단순히 행 번호로 붙이면 안 된다.

AI에는 ‘응답 시간·사람 ID·메뉴를 추출, 개인별 마지막 기록 표시, 이전 기록을 취소로 분리, 명부 결합, 세 집계표와 합계 검산’처럼 단계와 출력 컬럼을 지정한다. 이미지 판독 결과와 경계 시각은 원문으로 확인한다.

## 구독 비용 4문항

9개 플랜 정책 4쪽과 내부감사팀 보고서를 읽었다. 다른 14팀의 전체 사용 내역·181명 명부까지 독립 재집계하지 않았으므로 **2-4번의 최종 팀 코드·전사 금액은 확정하지 않는다.** 질문별 계산 방법은 다음과 같다.

| 문항 | 필요한 판정 |
| --- | --- |
| 1 | 내부감사팀의 사용 기능은 텍스트 생성·문서 요약. S1-S3에는 문서 요약이 없어 다운그레이드 불가. 독립 선택은 4번 |
| 2 | A2 팀만 필터한 뒤 팀 전체 사용량에서 공동 제공 크레딧을 빼 추가 과금액 비교 |
| 3 | 하위 플랜마다 기능 지원 AND 최소 인원 AND 초과요금 포함 월 총비용 감소를 검사하고 절감액 최대 팀 선택 |
| 4 | 5월 사용 기록에 한 번도 등장하지 않은 라이선스를 찾고 해당 인당 월 구독료를 합산 |

| 플랜 | 인당 월요금 USD | 인당 제공 크레딧 | 초과 단가 USD | 최소 인원 |
| --- | ---: | ---: | ---: | ---: |
| S1 | 12 | 5,000 | 0.006 | 3 |
| S2 | 20 | 10,000 | 0.005 | 5 |
| S3 | 28 | 15,000 | 0.004 | 5 |
| A1 | 40 | 20,000 | 0.0035 | 8 |
| A2 | 50 | 30,000 | 0.003 | 10 |
| A3 | 65 | 45,000 | 0.0025 | 10 |
| E1 | 80 | 60,000 | 0.002 | 15 |
| E2 | 100 | 80,000 | 추가 과금 없음 | 20 |
| E3 | 140 | 120,000 | 추가 과금 없음 | 25 |

제공 크레딧은 팀 안에서 풀링되며 남은 양은 이월되지 않는다. `N=계약 라이선스 수, p=인당 요금, c=인당 크레딧, U=팀 사용량, r=초과 단가`일 때 유료 초과 플랜의 월비용은 `N*p + max(0,U-N*c)*r`다. E2·E3은 별도 규칙을 따른다. 개인별 초과를 각각 과금하면 풀링 규칙을 어긴다.

실제 대조한 내부감사팀은 A3·10개 라이선스·85,000크레딧이다. 제공량 450,000 이내라 현재 구독료는 650달러다. 텍스트·문서 요약을 지원하고 최소 8명을 요구하는 A1로 바꾸면 10명 기준 제공량 200,000 이내에서 400달러가 되어 **월 250달러 절감**이다. 이는 한 팀의 계산 예시이며 전체 팀 중 최대 절감이라고 확정한 결과는 아니다.

주의할 점은 다음과 같다.

- 퇴사·휴직·군복무만으로 라이선스를 이미 회수했다고 가정하지 않는다. 문제는 별도 회수 정책이 없으면 유지한다고 명시한다.
- ‘사용량 0’과 ‘5월 기록에 전혀 등장하지 않음’의 정의를 구분한다. 이름 대신 사번·라이선스 ID를 기준으로 대조한다.
- 4번은 **월 구독료 합계**를 묻는다. 회수 후 줄어드는 풀 크레딧 때문에 늘어날 수 있는 미래 초과요금까지 추정하여 답을 바꾸지 않는다.
- 팀 코드의 표기·선행 0은 입력칸 형식과 자료를 대조한다. 하이픈·자리수를 임의로 바꾸지 않는다.

파일 토큰 총합은 43,720이다. 20,000 첨부 한도 안에서 정책과 대상 팀을 분할한다. 인사 명부는 4번에 필요하며 다른 문항에 항상 넣을 필요는 없다. 각 팀 결과를 `팀/플랜/N/U/사용기능/현재비용/후보플랜/후보비용/불가사유/근거`로 정규화한다.

## 규정 위반 4문항

국가 업데이트 3쪽과 YHC 첫 상품 2쪽을 대조했다. 일반 준법 가이드 전체와 45개 상품을 모두 재판정하지 않았으므로 전체 코드 목록을 공식 정답처럼 제시하지 않는다.

| 문항 | 논리 조건 |
| --- | --- |
| 1 | 지정 브랜드의 3상품 중 한국 등록 가능 AND EU 추가 규정 불충족 |
| 2 | 지정 검수자 AND Pass 처리 AND 의학적 효능 표현 위반 |
| 3 | Pass 처리 AND (성분 한도 초과 OR 금지 원료) |
| 4 | 모든 상품 중 한국 등록 가능 AND EU 추가 규정 불충족 |

업데이트는 2026년 3월 1일 발효되며 충돌 시 해당 규정이 일반 가이드보다 우선한다. 확인한 **문제 내부 규칙**은 레티놀 일반 한도 0.5와 EU 한도 0.3, 옥시벤존의 EU 배송 금지다. 실제 법령의 전체 내용으로 일반화하지 않는다.

YHC 첫 상품에서 레티놀 0.4를 확인했다. 이는 `0.4 <= 0.5`와 `0.4 > 0.3`을 동시에 만족해 **YHC-01은 1번의 우선 검증 후보**다. 한국의 나머지 표현·등록 요건과 다른 2상품까지 대조한 정답 확정과는 구분한다.

AI가 원문의 Pass 도장을 정답으로 받아들이지 않도록 ‘검수 결과는 비교 대상이며 규정 충족의 증거로 쓰지 말라’고 지시한다. 상품별 `코드/국가/유형/성분·단위/효능표현/검수자/기존판정/KR재판정/EU재판정/위반조항` 표를 만든다. 한국에서도 불가한 상품은 1·4번에서 제외한다. 상한과 같은 값은 ‘초과’와 다르고, %·mg·1회량·1일량의 분모를 일치시켜야 한다.

규칙 두 파일은 12,077토큰이므로 약 2,300토큰 상품 3개를 함께 넣으면 약 19,000토큰이다. 45개를 이 방식으로 처리하려면 많은 요청이 필요한다. 공통 규칙을 먼저 요약·검산한 뒤 필요한 조항과 대상 묶음으로 좁힌다. 모든 결과를 합칠 때 파일 누락·중복, 정렬, 쉼표·공백 형식을 확인한다. 정확한 호출 예산은 실제 카운터 범위를 보고 정한다.

## 교육 효과성과 커리큘럼 보고서

사전·사후 성과 CSV, 학과 활용도 CSV, 취업 CSV, 논의 TXT를 읽었다. 보고서는 효과성, 학과 수요, 벤치마크, Core+Track, 예산·ROI, 리스크·실행 일정의 여섯 영역을 요구한다. 전문 샘플은 자료 선택·지시·비판적 검증·보안과 산출물의 정확성·논리성을 함께 평가한다고 명시한다.

독립 계산 결과는 다음과 같다.

| 지표 | 검산 결과 |
| --- | ---: |
| 평가 인원 | 1,235명 |
| 인원 가중 사전 평균 | 51.0688 |
| 인원 가중 사후 평균 | 68.6672 |
| 상승폭 | 17.5984점 |
| 75점 목표까지 부족 | 6.3328점 |
| 컴퓨터공학 사후 가중평균 | 82.6581 |
| 인문학 사후 가중평균 | 53.6207 |
| 두 학과의 사후 격차 | 29.0374점 |

전체 평균은 `sum(인원*평균)/sum(인원)`이다. 14개 행을 단순 평균하면 67.6786으로 다른 값이 된다. 교육으로 점수가 올랐지만 목표와 학과 격차는 남았다. 따라서 ‘완전 실패’와 ‘성공하여 개선 불필요’ 모두 자료를 충분히 설명하지 못한다.

1-2학년 평가 자료와 4학년 취업 자료는 모집단·시점이 다르다. 높은 AI 점수와 취업률의 연관성만으로 해당 교육의 인과효과나 금전 ROI를 확정할 수 없다. 교수진 허용·과제 허용·학생 활용도에도 차이가 있어 학생 개인의 역량 부족만으로 원인을 단정하지 않는다.

논의 기록의 콘텐츠 850,000달러·교수진 교육 최소 200,000달러·기술비 최대 350,000달러를 모두 배분하면 총 1,400,000달러로 여유가 없다. **최대 금액은 반드시 지출해야 할 금액이 아니다.** 기술비를 줄일 수 있는 견적·라이선스 조건을 확인하여 버퍼를 설계한다. 공식 예산 이메일과 교차 확인한 뒤 확정한다.

Core는 공통 기초·데이터 소양·책임 있는 활용으로 두고 Track은 학과 수요에 맞춘다. 인문학 트랙을 뒤로 미루는 안은 논의의 이해관계자 요구와 충돌한다. 6월 동시 출범·9월 예비 보고라는 일정 안에서 최소 공통 성과 기준, 담당자, 비용, 평가 시점, 확대 조건을 연결한다. 실명·이메일은 프롬프트와 최종 보고서에서 역할·코드로 표현한다.

## 주문 조회 API 보고서

운영 코드, 서버 오류, 쿼리 추적, API 명세, 스키마, 변경 이력, 긴급 요청·QA 자료와 주문·아이템 CSV를 대조했다. 전체 레포·DB·재현 서버는 제공되지 않는다. 요구 산출물은 오류 원인, 성능 원인, 개선안, 테스트 5-8개의 보고서이며 여기의 개선안은 실행된 수정이나 성능 측정 결과가 아니다.

### 실제 500 경로

로그에는 `customerId=abc`가 SQL 조건에 문자열로 삽입되고, `orders.customer_id BIGINT`에서 형식 오류가 발생한 뒤 500으로 반환된 경로가 있다. 코드 11행의 입력 취득 → 18-24행 문자열 SQL → 26행 실행 → 63-69행 일괄 500 처리와 대조된다. 명세는 누락·형식·범위 오류를 400으로 요구한다.

입력 검증을 DB 연결·조회보다 먼저 수행하고 양의 정수·BIGINT 범위를 검사한다. SQL은 파라미터 바인딩으로 바꾼다. 내부 장애는 명세의 일반 메시지와 서버 로그로 구분하며 현재 `detail=str(e)`를 그대로 노출하는 응답도 검토한다. 커서·연결을 닫는 finally가 있으므로 **자료 근거 없이 연결 누수로 단정하지 않는다.**

### 성능의 정량 근거

쿼리 추적의 실제 한 요청은 주문 목록 1회와 10개 주문의 아이템 조회 10회, 총 11회다. 제시된 duration_ms 합은 56ms, 요청 전체는 213ms다. 전체 지연을 SQL 실행 시간과 동일시하지 않는다. 2회 일괄 조회로 바꾸면 이 사례의 조회 수는 약 81.8% 줄지만 응답 시간이 같은 비율로 줄어든다고 보장할 수 없다.

모니터링의 같은 09시 구간에서 2월 22일→28일 p95는 450→720ms, 오류율은 0.1→2.3%, 연결 지표는 35→52%다. 부하가 증가했으나 이 표만으로 각 원인의 기여도를 분해할 수 없다. 스키마에는 PK 외 인덱스가 없어 `orders(customer_id, created_at)`와 `order_items(order_id)` 계열의 인덱스를 실행계획으로 검토한다.

2월 25일 페이지 크기 확대는 미배포이고 20일 상태 필터는 롤백됐다. 현재 코드는 LIMIT 20이다. QA의 ‘주문 100개’ 설명을 현재 운영 경로의 사실로 그대로 사용하지 않는다. 출처·버전·배포 시점을 확인하고 실제 코드·트레이스와 충돌을 표시한다.

### 개선 순서와 호환성

긴급 요청의 우선순위는 정오까지 500 임시 조치, 당일 근본 분석·영구안, 기존 응답 형식 유지다. 우선 입력 검증·400 응답·SQL 바인딩을 제안하고, 이후 N+1 해소·인덱스·실행계획·부하 검증을 진행한다.

주문 20개를 먼저 선택한 뒤 해당 ID들의 아이템을 일괄 조회하여 묶는 방식은 부모·자식 구조를 보존하기 쉽다. JOIN된 평면 행에 LIMIT 20을 적용하면 주문 수·아이템 수가 왜곡될 수 있다. 주문 정렬, 아이템 정렬, 빈 items 배열, 다섯 status, unitPriceCents 단위와 JSON 구조를 유지한다. 임시 캐시는 주문 상태 갱신의 지연·무효화·키 설계·정확성 요구를 검토한 뒤 결정한다.

| 제안 테스트 | 확인 기준 |
| --- | --- |
| 정상 고객 101 | 제공 샘플의 주문 10개·아이템 22개, 정렬·필드·금액 단위 유지 |
| 주문 없는 고객 fixture | 200과 빈 orders. 존재 여부는 별도 fixture로 통제 |
| customerId 누락·빈 값 | 명세의 400 형식, DB 조회 전에 차단 |
| abc·0·음수·BIGINT 초과 | 500 대신 400. 경계는 정의된 계약과 일치 |
| SQL 특수문자 입력 | 검증 및 바인딩으로 데이터 범위가 바뀌지 않음 |
| 복수·빈 아이템 fixture | 주문 중복·누락 없이 아이템 정렬과 빈 배열 유지 |
| 최대 20주문 부하 fixture | 조회 수 제한, 회귀 전후 p95·DB 부하·오류율 비교 |
| 실제 DB 장애 fixture | 일반 500 응답, 내부 상세는 사용자 응답에 노출하지 않음 |

실제 실행하지 않은 테스트는 통과했다고 쓰지 않는다. 담당자 실명·이메일은 역할로 표현한다.

## 남은 기간의 준비 우선순위

첫째, 지식 샘플의 10개 개념과 조건 소거 방식을 익힌다. 둘째, 자료의 마지막 상태·AND 조건·문서 우선순위·분모·단위·출력 형식을 직접 검사한다. 셋째, 파일 열람과 AI 첨부·채팅과 제출 칸을 구분하는 UI 조작을 체험한다. 전문 사례는 익숙한 영역 하나를 골라 요구 섹션·근거·검증을 빠짐없이 작성하는 연습에 활용한다.

30분을 지식, 90분을 활용·서술형 방식으로 대비하는 것은 시간과 샘플에 따른 준비 가설이다. 실제 세션 명칭·문항 수·배점은 본인 초대에서 확인한다. 남은 시간을 방대한 ML 수학·새 에이전트 앱 개발·대형 모델 설치에 먼저 쓰기보다 자료 검증과 실제 환경 검사에 배분한다.

당일 절차·일본 회선·설치본·Git 상태는 [루트 당일 안내](../../README.md)를 따른다. 샘플 해설이 합격선·출제 비중·정답 채점·실전 도구 허용을 보장하지 않는다.

### 호출 수와 자료 처리의 병목

기록된 규칙12,077토큰과 상품 약2,300토큰을 함께 첨부하면 3상품에18,977토큰이다. 이 방식으로45상품을 처리하려면15회이며 병합·오류 검증 호출은 추가다. 따라서 10회 예산이라면 원본 규칙을 매번 붙이는 방식은 예산을 초과한다. 실제 적용 카운터의 단위를 로그인 후 확인해야 한다.

압축한 규칙과 더 큰 상품 묶음을 이용하는 방식은 후보 전략이다. 예외·효력일·단위·우선순위가 빠지지 않았는지 원문으로 확인하고, 이전 첨부를 제거했을 때 기준이 어떻게 유지되는지 실제 UI에서 확인해야 한다. 아직 검증된10회 완주 절차나 자동화 도구가 구현된 상태는 아니다.

구독43,720토큰도20,000으로 나누면 최소3묶음이라는 이론적 하한일 뿐이다. 공통 정책의 반복 첨부·파일별 크기·검산 요청을 포함한 실제 호출 수는 별도로 산정한다.

### 로그인 후 완료할 검증 순서

1. 전체 파일 목록을 기록하고 파일별 `읽음 / AI첨부 / 추출 / 독립검산 / 최종반영` 상태를 구분한다.
2. 각 질문의 대상·기간·AND/OR 괄호·단위·예외·정렬·출력 형식을 추출한다.
3. 구독의 모든 팀·인원과 규정의45상품을 빠짐없이 판정한다. 오류·미확정 값을 별도로 남긴다.
4. 대화 예산 안에 들어오는 자료 묶음과 공통 기준 보존 방식을 설계한다. 원문을 보존한 상태로 요약 손실을 대조한다.
5. 실제 AI 질문을 사용하는 실험 전 잔여 횟수를 확인한다. 사용한 횟수는 초기화되지 않으므로 소모가 필요한 검증은 범위를 정해 진행한다.
6. 요구 답안 형식으로 완성하고 질문별 근거·누락·중복·합계·정렬·보고서 섹션을 독립 확인한다.

타임스탬프가 같은 신청 기록이 있다면 자료의 우선 규칙을 확인하고 임의로 마지막 행을 선택하지 않는다. 구독에서는 ‘한 번도 등장하지 않음’과 ‘사용량0’, 규정에서는 기존 Pass와 실제 적합성을 구분한다.

### 준비 완료 판정

파일·문법·링크·복구 설치본의 무결성은 로컬에서 확인할 수 있다. 해당 실행 결과는 `private/`에 기기별로 저장한다. 이 작업 PC에서 설치본을 현재 `offline/installers/` 경로에 맞추고 크기·SHA256·게시자 서명 검사를 통과했다. 다른 노트북에 clone하면 설치본과 개인 기록은 별도로 옮겨 확인해야 한다.

현재 판정은 **당일 절차 안내와 풀이 전략으로 사용 가능, 전체 자료 검증·제한 내 완주·본인 실전 응시 환경은 미완료**다. 로그인 후 원자료 검증과 공식 사전점검 없이 완전한 즉시 응시 상태라고 표시하지 않는다.
