# SK하이닉스 산업 AI 배경과 사전 연습 프로젝트

기준일은 2026년 10월 13일 KST이다. 신청을 마쳤고 웹 개발 경험이 있는 참가자라면, 1차 예선 전에는 반도체 용어를 짧게 익힌 뒤 **표와 로그를 정확히 읽고, AI의 답을 근거와 계산으로 검증하는 연습**에 집중하는 편이 좋다. 이 문서의 산업 사례는 실제 SK하이닉스 공개 사례이고, 연습 프로젝트와 시간 배분은 준비를 위한 제안이다. 아래 프로젝트가 이번 대회에 출제된다는 뜻은 아니다.

대회 홈페이지는 1차 예선을 AI 기초 지식 및 활용 역량 검증으로, 본선을 반도체 현장의 고민을 AI로 해결하는 과정으로 설명한다. 공개 문구만으로 1차에 반도체 전문 시험이나 모델 학습 과제가 나온다고 단정할 수 없다. **10월 17일 또는 18일의 1차 예선까지 도메인 학습은 전체 준비 시간의 20% 이내**로 두고, CNN 학습·대용량 데이터·GPU 환경 구성은 1차 이후로 미룬다. [대회 공식 홈페이지](https://skhynix-hackathon.com/ai-2026)

## 먼저 익힐 반도체 개념

### 메모리 제품과 AI의 연결

| 개념 | 이해할 핵심 | AI 서비스를 만들 때 연결할 질문 |
| --- | --- | --- |
| DRAM | 작동 중인 프로그램과 데이터를 빠르게 읽고 쓰는 휘발성 메모리다. 전원이 끊기면 데이터가 사라지고 주기적인 리프레시가 필요하다. | 모델과 캐시가 메모리에 들어가는가, 동시 요청을 얼마나 받을 수 있는가 |
| NAND Flash | 전원이 없어도 데이터를 보존하는 비휘발성 메모리이며 SSD의 저장 매체에 사용된다. | 문서·로그·체크포인트를 어디에 저장하고 얼마나 빨리 읽을 수 있는가 |
| HBM | 여러 DRAM 칩을 수직으로 연결해 높은 대역폭을 제공하는 메모리다. | 연산기가 데이터를 기다리는 병목을 어떻게 줄이는가 |
| SSD와 eSSD | SSD는 NAND뿐 아니라 컨트롤러와 펌웨어를 포함하는 저장 장치다. eSSD는 기업용 SSD를 뜻한다. | 저장 용량 외에 읽기·쓰기 지연, 처리량, 신뢰성과 펌웨어 오류가 중요한가 |

DRAM과 NAND의 기본 구분은 [SK하이닉스 Semiconductor 101](https://news.skhynix.com/en/semiconductor-101-sk-hynix-explains-whats-what-in-the-semiconductor-world/)과 [DRAM 정의](https://news.skhynix.com/en/semiconductor-101-sk-hynix-guide-to-key-industry-players/)를, HBM의 구조와 현재 제품 맥락은 [MWC 2026 공식 소개](https://news.skhynix.com/en/mwc-2026/)를 참고하면 된다. SSD 펌웨어와 규격 검증은 [실제 GaiA 로그 분석 사례](https://news.skhynix.co.kr/gaia_ep1_biz_ai_agent/)에서 확인할 수 있다.

SK하이닉스는 2026년 6월 18일 12단 HBM4E 샘플을 주요 고객에게 공급했다고 발표했다. 여기서 샘플 공급, 개발 완료, 양산 준비, 실제 양산 공급은 각각 다른 단계다. 제품 세대와 숫자를 외우기보다 용량·대역폭·전력·발열·패키징 사이의 제약을 설명할 수 있으면 충분하다. [HBM4E 샘플 공급 공식 발표](https://news.skhynix.com/en/sk-hynix-ships-samples-of-12-layer-next-gen-hbm4e-2/)

### 제조 흐름과 데이터

반도체 제조는 웨이퍼 위에 소자를 만들고 배선으로 연결한 뒤 검사와 패키징을 거치는 복잡한 반복 과정이다. 산화·포토·식각·증착 등의 작업은 여러 단계에서 반복된다. 통상적인 8대 공정 분류는 입문용 개괄이며 실제 공정이 여덟 번의 작업으로 끝난다는 뜻은 아니다. [SK하이닉스 전공정 개괄 칼럼](https://news.skhynix.co.kr/jeonginseong-column-oxidation/)

다음 표는 사전 연습용 데이터 모델이다. 실제 대회의 데이터 필드와 SK하이닉스 내부 시스템 스키마를 재현한 것은 아니다.

| 데이터 단위 | 연습용 필드 예 | 분석 시 확인할 점 |
| --- | --- | --- |
| 생산 묶음과 제품 | lot_id, wafer_id, product_id | 동일 묶음의 샘플이 학습과 평가에 동시에 들어가는가 |
| 공정과 설비 | process_step, tool_id, chamber_id, recipe_version | 설비·제품·레시피 차이가 결과 차이와 섞여 있는가 |
| 센서 기록 | timestamp, temperature, pressure, flow | 단위, 시간대, 샘플링 주기, 센서 고장, 누락 구간 |
| 계측과 검사 | thickness, overlay, pass_fail, measured_at | 예측 시점에 계측 결과가 이미 존재했는가 |
| 불량 이미지와 맵 | wafer_map, defect_mask, camera_id | 원본과 복사·회전·크롭 이미지가 다른 분할로 들어갔는가 |
| 업무 문서와 로그 | document_id, revision, alarm_code, maintenance_note | 최신 문서인지, 주장에 맞는 근거인지, 처리 결과를 입력으로 잘못 썼는지 |

### 분석 문제를 구분하는 용어

| 용어 | 설명 | 흔한 오류 |
| --- | --- | --- |
| 수율 Yield | 정의한 검사 단위 중 양품의 비율. 웨이퍼·다이·패키지 등 분모를 먼저 정한다. | 서로 다른 제품의 수율을 단순 평균하고 생산량 차이를 무시 |
| 계측 Metrology | 두께·치수·정렬 등 공정 결과를 측정 | 검사 합격·불합격만을 계측값과 같은 것으로 취급 |
| 가상계측 VM | 장비·공정 데이터로 실제 계측값을 예측 | 예측값을 실측값으로 표시하거나 미계측 전부를 검증됐다고 설명 |
| SPC | 통계적 공정 관리. 정상 기준에서 공정이 달라지는지 관찰 | 관리한계와 제품 규격한계를 같은 값으로 사용 |
| FDC | 설비 이상을 탐지하고 분류하는 접근 | 이상 점수를 곧바로 물리적 고장 원인이라고 단정 |
| APC | 공정 조건을 최적화하는 제어 접근 | 예측 모델의 상관관계를 근거로 실제 레시피를 자동 변경 |
| SOP와 Inform Note | SOP는 표준 작업 절차, Inform Note는 장비 이상과 조치 등 인수인계 기록 | 옛 버전 절차를 현재 설비에 적용하거나 문서에 없는 조치를 생성 |
| EDA | 전자 설계 자동화. 데이터 분석의 탐색적 분석 EDA와 문맥이 다르다. | 설계 스크립트 문제를 일반 CSV 분석 문제로 오해 |

VM·APC는 [SK하이닉스 가상계측 도입 발표](https://news.skhynix.com/en/gauss-labss-ai-based-virtual-metrology-solution/), FDC는 [SK하이닉스 FDC 기술명장 소개](https://news.skhynix.co.kr/the-first-grade-hygineer-part2/), SOP·Inform Note·설계 EDA는 [Future Forum 2026](https://news.skhynix.com/en/future-forum-2026/)과 [GaiA 업무 사례](https://news.skhynix.co.kr/gaia_ep1_biz_ai_agent/)를 참고한다. SPC의 통계적 의미는 [NIST 관리도 설명](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc31.htm)과 [NIST 공정능력 설명](https://www.itl.nist.gov/div898/handbook/pmc/section1/pmc16.htm)이 유용하다.

## SK하이닉스가 공개한 산업 AI 사례

### GaiA의 업무 AI Agent

2025년 10월 31일 SK하이닉스는 GaiA 기반 Biz AI Agent 네 종류를 소개했다. 아래 기능과 성과는 회사 공개 자료의 내용이며, 참가자가 접근할 수 있는 내부 서비스나 이번 대회의 지정 도구라는 뜻은 아니다. [GaiA 공식 사례 소개](https://news.skhynix.co.kr/gaia_ep1_biz_ai_agent/)

| 공개 사례 | 해결하려는 업무 | 웹 개발자가 연습할 구현 |
| --- | --- | --- |
| Inform Note 기반 장비 보전 가이드 | 장비 이력 요약과 불량 조치 가이드 | 합성 정비 기록 검색, 설비·날짜 필터, 근거가 있는 답변 |
| EDA Scripts 검색과 생성 | 설계 문서 검색 및 설계·검증 코드 작성 | 문서에서 API 사용법 검색, 코드 생성, 실행 결과 확인 |
| AI 기반 로그 분석 자동화 | SSD 등 제품 테스트 로그와 NVMe 규격을 비교해 문제 분석 | 오류 코드 추출, 시간 순서 정리, 규칙 위반 후보와 근거 링크 |
| Global Insight | 외부 정책·시장·기술 자료와 문서 분석을 통한 의사결정 지원 | 출처·날짜를 보존한 검색, 상충하는 주장 비교, 사실과 해석 분리 |

회사는 SSD 스펙 관련 불량 분석 시간이 20% 이상 줄었다고 밝혔다. 이 숫자는 특정 사내 업무의 발표 성과이며, 임의의 RAG 데모에서 동일 효과가 나온다는 보장은 없다. 연습에서는 시간 절감률을 주장하기 전에 동일 질문을 사람이 처리하는 기준 시간을 정하고 정확성도 함께 측정한다. [해당 공식 사례](https://news.skhynix.co.kr/gaia_ep1_biz_ai_agent/)

### 센서 기반 가상계측

SK하이닉스는 2022년 12월부터 Gauss Labs의 Panoptes VM을 박막 증착 공정에 활용했다고 2023년 1월 발표했다. 장비 센서 데이터로 두께와 굴절률 등 공정 결과를 예측하고 APC와 연결해 공정 변동성을 평균 21.5% 줄였다는 내용이다. **공정 변동성 21.5% 감소는 수율 21.5% 상승과 같은 지표가 아니다.** [SK하이닉스 공식 도입 발표](https://news.skhynix.com/en/gauss-labss-ai-based-virtual-metrology-solution/)

Gauss Labs의 현재 제품 설명은 VM을 공정 감시, 계측 샘플링 조정, 설비 보전, 공정 제어에 연결한다. 사전 연습의 핵심은 거대한 모델보다 장비 기록과 검사 결과를 올바른 시간·ID로 결합하는 일이다. [Panoptes VM 공식 제품 설명](https://www.gausslabs.ai/vm)

### 2026년의 인간 AI 협업 방향

2026년 9월 Future Forum에서는 SOP를 중심으로 업무를 재설계하고 공정·장비 데이터의 의미와 관계를 정의하는 접근을 소개했다. 라인 이상에 대해 AI가 원인과 대응 후보를 제시하고 사람이 최종 판단하는 업무를 전망했으며, GaiA와 안전 감시 로봇·VLM 드론 활용 계획도 언급했다. [Future Forum 공식 기사](https://news.skhynix.com/en/future-forum-2026/)

이 방향에서 사전 연습으로 이어지는 부분은 명확하다. AI가 관찰한 데이터, 제시한 가설, 참조한 문서, 확인해야 할 추가 정보를 화면과 출력 파일에서 구분한다. 설비 이름만 바꾼 일반 챗봇보다 이런 분석 과정을 검증할 수 있는 작은 도구가 산업 업무를 설명하기 쉽다.

## 사전 연습 프로젝트 비교

아래 순위와 소요 시간은 공개 대회의 출제 예측이 아니라 **웹 개발 경험이 있고 1차 예선이 임박한 참가자를 위한 준비 제안**이다. 시간은 정상적인 개발 환경과 데이터 접근이 확보된 뒤의 순수 구현 시간을 가정한다. 다운로드·환경 장애와 학습 시간은 별도로 잡는다.

| 번호 | 프로젝트 | 최소 구현 | 검증 지표 | 준비 순위와 예상 시간 |
| --- | --- | --- | --- | --- |
| 1 | 생산 CSV 분석과 불량 위험 설명 | 집계·데이터 품질 검사·단순 분류 기준 | 집계 정답, AP, 불량 recall, 경고 수 | 1차 전 최우선. CSV 분석 60~90분, 모델은 이후 3~5시간 |
| 2 | 근거 문서를 붙이는 로그 분석 도우미 | 오류 추출·문서 검색·근거 인용·답변 보류 | 근거 정확성, 미지원 질문 처리, 조치 오류 | 1차 전 최우선. 작은 합성 자료 90~120분 |
| 3 | 센서 이상 경보와 SPC 비교 | 정상 기준선·이상 점수·시간 표시 | 사건 recall, 오경보/일, 탐지 지연 | 1차 이후 우선. 4~6시간 |
| 4 | 설비 고장 위험과 점검 우선순위 | 단순 분류·임계값·점검 큐 | AP, 비용별 recall, calibration | 1차 이후 우선. 3~5시간 |
| 5 | 웨이퍼 불량 패턴 분류 | 합성 맵 규칙 또는 작은 분류기 | macro F1, 클래스별 recall, unknown 거절 | 도메인 확장. 5~8시간 이상 |
| 6 | 정상 이미지 기반 결함 탐지 | 한 품목의 임베딩과 최근접 이상 점수 | 이미지 AP/AUROC, 픽셀 위치 지표, 지연 | GPU 준비 후 선택. 6~10시간 이상 |
| 7 | 공정 조건 실험 계획 | 합성 함수·무작위 탐색·제약을 둔 최적화 | 평가 횟수별 최고값, 제약 위반, 비용 | 본선 대비 선택. 4~8시간 |
| 8 | LLM 메모리와 응답 비용 분석 | 모델·문맥 길이·동시 요청별 계산기 | 계산 단위 검증, 실측 지연·메모리 | 개념은 15~30분. 실측은 2~4시간 |

1차 전에는 1번의 집계·검증 부분과 2번만 수행해도 된다. 3~8번 전체를 사전에 완성하려고 하면 AI 기초와 시간 제한 문제 해결 연습을 잠식할 수 있다.

### 프로젝트 1 생산 CSV 분석과 불량 위험 설명

**문제 정의:** 어떤 제품·설비·기간에서 불량 비율이 높고, 어떤 샘플을 추가 확인해야 하는지 재현 가능한 표로 설명한다. 통계 집계와 예측은 서로 다른 결과로 표시한다.

**공개 데이터:** UCI SECOM은 반도체 제조 공정의 익명화된 고차원 센서 데이터로, 1,567개 샘플 중 불량은 104개다. 결측값이 있으며 라벨 파일에 시간 정보가 있다. 라이선스는 CC BY 4.0이다. 공개 페이지의 특성 수 표기와 실제 파일 열 수는 가져온 파일의 스키마로 확인한다. [UCI SECOM](https://archive.ics.uci.edu/dataset/179/secom)

불량 104개라는 공개 수치에서 계산하면 불량률은 약 6.64%다. 모든 샘플을 정상으로 답해도 정확도는 약 93.36%이므로 정확도만 제시하면 의미가 작다. SECOM에는 이해하기 쉬운 공정 이름이나 설비 이름이 제공되지 않으므로 익명 센서를 실제 압력·온도·SK하이닉스 특정 장비로 해석하지 않는다.

**최소 구현:** 1차 전에는 프로젝트 폴더의 합성 생산 CSV로 행 수, 유일 ID 수, 결측 수, 중복, 제품별 분모, 생산량 가중 수율을 계산한다. 이후 SECOM에서 중앙값 대치와 단순 분류기를 비교한다. 중요 센서는 모델이 참고하는 변수로 표현한다.

**누수 방지:** 분할 뒤 학습 데이터만으로 결측 대치·스케일·특성 선택을 학습한다. 불량의 사후 검사 결과·처리 조치·최종 승인 상태를 예측 시점 입력으로 넣지 않는다. 시간 분할에서 불량 표본이 너무 적으면 그 한계를 보고하고, 무작위 분할 결과는 보조 비교로 표시한다. 이런 전처리 원칙은 [scikit-learn 공식 권장 사항](https://scikit-learn.org/stable/common_pitfalls.html)과 맞는다.

**평가:** 불량 recall, precision, Average Precision, 혼동행렬과 경고 샘플 수를 함께 출력한다. AP를 사다리꼴로 계산한 PR AUC와 무조건 같은 값으로 표시하지 않는다. [AP 정의](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html)

**완성 기준:** 같은 입력에서 같은 집계가 나오고, 분모·제외 행·정상 기준선·평가 분할·샘플 수가 보고서에 나온다. 미검증 상태에서 실제 수율 개선률을 주장하지 않는다.

### 프로젝트 2 근거 문서를 붙이는 로그 분석 도우미

**문제 정의:** 로그에서 오류와 발생 순서를 찾고, 적용되는 문서 규칙과 원인 후보를 설명한다. 실제 GaiA 장비 보전과 로그 분석 업무에 연결되는 연습이다. [GaiA 공개 업무 사례](https://news.skhynix.co.kr/gaia_ep1_biz_ai_agent/)

**자료:** 직접 작성한 합성 정비 노트 10~20개와 합성 테스트 로그를 쓴다. 문서마다 `document_id`, `equipment_model`, `revision`, `valid_from`, `section`을 붙인다. SK하이닉스 뉴스룸은 업무 맥락을 학습하는 참고 자료이며, 공개 기사에서 실제 설비 SOP나 내부 Inform Note를 추출할 수 있다고 가정하지 않는다. 공개 표준을 추가할 때는 해당 배포 조건과 대회 외부 자료 규정을 먼저 확인한다.

**최소 구현:** 정규식 또는 JSON 파서로 오류 코드를 추출하고, 키워드 검색으로 관련 문서를 찾는다. LLM 출력은 `관찰 사실`, `원인 후보`, `근거 문서`, `추가 확인`, `판단 가능 여부`로 구조화한다. 모델의 긴 답변보다 근거를 클릭해서 실제 조항을 확인할 수 있게 만든다.

**검증 세트:** 문서에서 답할 수 있는 질문 10개, 근거가 없는 질문 5개, 옛 버전 문서와 충돌하는 질문 3개, 장비 모델이 다른 질문 2개를 만든다. 평가 질문의 모범 답안을 검색 대상 문서에 넣지 않는다.

**평가:** 인용한 근거가 해당 주장에 맞는 비율, 답해야 할 질문의 정답률, 근거 없는 질문의 보류율, 잘못된 조치 제안 수, 처리 시간을 기록한다. 자동 채점용 LLM의 점수만으로 완료하지 않고 작은 세트는 사람이 판정한다.

**완성 기준:** 일부만 근거가 있으면 확인된 부분만 답하며, 오래된 절차를 현재 절차로 제시하지 않는다. 로그 시간과 표준 조항을 화면에서 추적할 수 있다. 웹 개발자는 이 데이터 흐름을 기존 API·폼·상태 관리 경험으로 구현할 수 있다.

### 프로젝트 3 센서 이상 경보와 SPC 비교

**문제 정의:** 언제 공정 상태가 변했고, 어느 센서가 확인 대상인지 경보한다. 미래 고장까지 예측했는지는 별도의 문제다.

**공개 데이터:** UCI Hydraulic Systems는 60초 반복 부하 주기의 유압 시험대 데이터이며 2,205개 주기에 압력·온도·유량 등과 부품 상태 라벨이 있다. 센서마다 샘플링 주기가 다르다. CC BY 4.0으로 배포되며 반도체 설비 데이터는 아니다. [UCI Hydraulic Systems](https://archive.ics.uci.edu/dataset/447)

**최소 구현:** 우선 센서별 주기 평균·표준편차·최솟값·최댓값으로 작게 만들고 정상 상태의 기준선을 구한다. 단일 변수 관리도와 단순 이상 탐지기를 비교한다. 센서를 결합할 때 100 Hz 압력과 1 Hz 온도의 시점을 무심코 같은 열 번호로 맞추지 않는다.

**누수 방지:** 같은 60초 주기를 여러 창으로 나누었다면 창들을 같은 분할에 둔다. 전체 데이터로 정상 평균이나 이상 임계값을 결정하지 않는다. 실험 주기의 순서를 장기간 자연 열화나 실제 설비 수명 이력으로 해석하지 않는다.

**평가:** 경보를 매 시점의 점수에서 사건 단위로 묶어 사건 recall·오경보 빈도·지연을 출력한다. 이 데이터에서 현실적인 고장 사건 시각이 정의되지 않으면 주기별 상태 판정 지표만 보고하고 탐지 지연은 합성 시나리오에서 측정한다.

**SPC 학습 포인트:** 관리한계는 정상 공정의 변동을 기반으로 정하고, 규격한계는 요구되는 제품 허용 범위를 나타낸다. 분포·자기상관·공정 변경에 따라 단순한 3σ 경보의 의미가 달라진다. 공정능력 지수는 안정성과 분포 가정을 확인한 뒤 해석한다. [NIST 관리도](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc31.htm), [NIST 공정능력](https://www.itl.nist.gov/div898/handbook/pmc/section1/pmc16.htm)

### 프로젝트 4 설비 고장 위험과 점검 우선순위

**문제 정의:** 제한된 점검 인력으로 고장 가능성이 높은 사례를 먼저 검토한다. 현재 고장 판정과 잔여 수명 예측을 구별한다.

**공개 데이터:** UCI AI4I 2020은 10,000행 합성 예지 정비 데이터로 제품 종류, 온도, 회전수, 토크, 공구 마모 등 여섯 입력 특성과 고장 라벨을 제공한다. 공식 페이지의 14개 전체 열에는 ID와 여러 타깃도 포함된다. CC BY 4.0이다. [UCI AI4I 2020](https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset)

**최소 구현:** 단순 규칙과 분류기를 비교하고 경고 임계값에 따라 점검 건수가 어떻게 바뀌는지 보여준다. 온도는 K, 회전수는 rpm, 토크는 Nm라는 단위를 보존한다. `Machine failure`를 예측할 때 `TWF`, `HDF`, `PWF`, `OSF`, `RNF` 등 고장 모드 타깃을 입력에 포함하면 정답 정보가 새어 나갈 수 있다. `UID`와 제품 일련번호도 먼저 제거해 평가한다.

**평가:** AP, 고장 recall과 점검 예산별 recall, 확률 calibration을 본다. 예를 들어 하루 20건만 점검할 수 있다고 가정한 정책을 만들고 그 가정을 명시한다. 비용은 합성 가정으로 두며 실제 드라이펌프 경제성으로 표현하지 않는다.

**한계:** 이 데이터로 실제 SK하이닉스 설비의 수명이나 몇 시간 뒤 고장을 검증할 수 없다. 데이터 생성 규칙을 잘 복원한 점수를 현실 일반화로 설명하지 않는다.

**수명 예측 확장:** NASA C-MAPSS는 여러 엔진의 시계열과 잔여 운전 주기 예측을 연습하는 별도 자료다. 엔진별로 분할하고 RMSE·MAE와 위험한 과대 수명 예측을 따로 본다. 반도체 장비에 대한 직접 성능 근거는 아니다. NASA 공식 저장소는 해당 데이터 다운로드를 안내하지만, 별도의 C-MAPSS 시뮬레이터 페이지는 소프트웨어 이용 불가를 공지한다. 데이터와 시뮬레이터를 혼동하지 않는다. 데이터 라이선스는 내려받은 배포본에서 확인한다. [NASA PCoE 데이터 저장소](https://www.nasa.gov/intelligent-systems-division/discovery-and-systems-health/pcoe/pcoe-data-set-repository/), [C-MAPSS 데이터 설명](https://data.nasa.gov/dataset/cmapss-jet-engine-simulated-data), [별도 시뮬레이터 자료 상태](https://data.nasa.gov/dataset/c-mapss-aircraft-engine-simulator-data)

### 프로젝트 5 웨이퍼 불량 패턴 분류

**문제 정의:** 공간적인 불량 패턴을 분류하고 비슷한 과거 맵을 찾는다. 패턴 분류에서 곧바로 실제 원인을 확정하지 않는다.

**공개 데이터와 권리:** WM-811K 원 논문에 대한 National Taiwan University 공식 기록은 811,457개 실제 웨이퍼 맵을 사용했다고 설명한다. 원 배포처 MIR Lab의 접근과 라이선스 문구는 이번 확인에서 확보되지 않았다. 따라서 제3자 미러의 CC0 표기를 원 데이터 사용 허가로 단정하지 않는다. [원 논문 대학 공식 기록](https://scholars.lib.ntu.edu.tw/entities/publication/563e8f2c-74ee-4733-bd62-ba5e409d8424), [원 배포처](http://mirlab.org/dataSet/public/)

**바로 가능한 대안:** 원형 영역 안에 중심·가장자리·선형 스크래치·무작위 불량을 넣은 합성 맵을 직접 만든다. 합성이라고 화면과 데이터 메타데이터에 적는다. 원 배포본 조건을 확인한 뒤 실제 공개 자료로 교체할 수 있도록 입력 파서와 분석 코드를 분리한다.

**최소 구현:** 불량 비율, 중심에서의 거리, 방향별 분포, 연결 영역 수 같은 단순 특성을 만든 뒤 분류기를 비교한다. 복잡한 CNN은 이후 확장한다. 실제 원인보다 `확인할 패턴`과 `불확실한 분류`를 보여준다.

**누수 방지:** 원본과 모든 회전·크롭·증강본을 같은 분할에 둔다. 실제 데이터에 lot ID가 있으면 lot 단위로 분할하고, 유사 맵·중복도 확인한다. 이미지 보간으로 정상·불량·배경이라는 이산 값이 섞이지 않도록 처리한다.

**평가:** macro F1과 클래스별 recall을 기본으로 하고 정상 클래스 포함 여부, 클래스별 평가 수, 원본 해상도와 전처리를 밝힌다. 논문의 높은 정확도를 서로 다른 분할·클래스 구성의 내 점수와 그대로 비교하지 않는다.

### 프로젝트 6 정상 이미지 기반 결함 탐지

**문제 정의:** 결함 사례가 적을 때 정상 외관에서 벗어난 이미지와 영역을 찾는다.

**공개 데이터:** MVTec AD는 15개 물체·텍스처 범주에 정상 학습 이미지, 정상·결함 평가 이미지와 픽셀 단위 결함 주석을 제공한다. 반도체 팹 이미지라고 볼 수는 없다. 데이터는 CC BY-NC-SA 4.0으로 배포되며 상업 사용을 금지한다. 개인 학습과 상금·채용 연계 대회 제출의 조건을 동일하게 가정하지 말고, 제출 전에 주최 측 자료 규정과 권리 조건을 확인한다. [MVTec AD 공식 페이지](https://www.mvtec.com/research-teaching/datasets/mvtec-ad)

**최소 구현:** 한 품목만 골라 사전 학습 임베딩과 최근접 거리로 이상 점수를 만들고 정상 학습 이미지만으로 기준을 세운다. PatchCore는 정상 패치 특성을 저장해 비교하는 접근이며 저자 공개 구현은 Apache 2.0이다. 코드 라이선스와 데이터 라이선스는 별개다. [PatchCore 저자 구현](https://github.com/amazon-science/patchcore-inspection)

**누수 방지:** 테스트 결함 이미지로 임계값·특성 추출기·이미지 크기를 계속 조정하면 테스트 결과가 낙관적으로 변한다. 정상 학습 세트 일부를 검증에 쓰고 테스트는 최종 평가에 남긴다.

**평가:** 이미지 수준 AP/AUROC와 결함 위치 평가를 구분한다. 픽셀 대부분이 정상인 상황에서 픽셀 정확도만 보고하지 않는다. 품목별 결과, 이미지 해상도, 처리 지연과 메모리도 출력한다.

**확장:** MVTec AD 2는 더 어려운 검사 상황과 조명 분포 변화 등을 포함하며 테스트 일부는 평가 서버를 통해 평가한다. 처음 시작할 때는 AD 한 품목이 간단하다. AD 2도 CC BY-NC-SA 4.0이다. [MVTec AD 2 공식 페이지](https://www.mvtec.com/research-teaching/datasets/mvtec-ad-2)

### 프로젝트 7 공정 조건 실험 계획

**문제 정의:** 제한된 실험 횟수로 목표 품질을 개선할 조건 후보를 고른다. 실제 설비 제어와 분리한 합성 연습이다.

**자료:** 입력 범위를 0~1로 정규화한 자체 합성 함수 또는 BoTorch의 표준 시험 함수를 사용한다. 함수가 실제 증착·식각 공정의 물리 모델이라고 주장하지 않는다. BoTorch는 Bayesian optimization용 공식 라이브러리이고 MIT 라이선스다. [BoTorch 공식 저장소](https://github.com/meta-pytorch/botorch)

**최소 구현:** 같은 총 평가 횟수에서 무작위 탐색과 최적화 방법을 비교한다. 온도·압력처럼 이름 붙인 입력의 단위와 허용 범위를 명시하고 `후보 조건 → 평가 → 결과 저장 → 다음 후보` 흐름을 시각화한다. 실험 설계는 관찰된 상관관계와 개입 효과를 구분하는 학습에 도움이 된다. [NIST 실험 설계](https://www.itl.nist.gov/div898/handbook/pri/section1/pri11.htm)

**평가:** 평가 횟수별 최고 목적값, 사용 비용, 제약 위반 횟수를 같은 초기 조건과 여러 seed에서 비교한다. 실패하거나 측정 불가능한 조건을 삭제하고 성공한 결과만 비교하지 않는다.

**완성 기준:** 위험한 조건은 실행 대상으로 내보내지 않고 사람이 검토할 후보로 제시한다. 단순 feature importance를 보고 `이 센서를 바꾸면 수율이 올라간다`고 설명하지 않는다. 설명 가능한 AI의 변수 기여도와 인과적 개입의 차이는 [Janzing 등의 원 논문](https://arxiv.org/abs/1910.13413)을 참고한다.

### 프로젝트 8 LLM 메모리와 응답 비용 분석

**문제 정의:** 모델을 선택할 때 문맥 길이·동시 요청·응답 품질·메모리·지연 사이의 선택을 수치로 설명한다. HBM을 만드는 회사의 AI 업무와 연결되는 개념 연습이다.

KV cache는 이미 처리한 토큰의 key와 value를 저장해 다음 토큰 생성에서 계산을 재사용한다. 문맥과 요청 수가 커지면 캐시도 커진다. PagedAttention 원 논문은 캐시 메모리 낭비와 중복을 줄이는 방법을 제안한다. 논문 속 속도 향상 수치는 해당 평가 조건의 결과다. [Hugging Face 캐시 설명](https://huggingface.co/docs/transformers/en/cache_explanation), [PagedAttention 원 논문](https://arxiv.org/abs/2309.06180)

**최소 구현:** 다음 계산식을 표시하는 작은 계산기를 만든다. 아래는 단순 추정식이며 실제 GPU 사용량은 런타임·활성값·메타데이터·양자화 방식·병렬화 등에 따라 달라진다.

```text
가중치 바이트 ≈ 파라미터 수 × 파라미터당 저장 바이트
KV 바이트 ≈ 2 × 레이어 수 × KV head 수 × head 차원
           × 저장한 토큰 수 × KV 값당 바이트 × 요청 수
```

가상의 7B 모델을 파라미터당 2바이트로만 저장한다면 가중치는 약 14 GB다. 가상의 `32 레이어, 8 KV heads, head 차원 128, 4096 토큰, 2바이트, 1요청`은 KV 약 512 MiB다. KV heads를 32개로 바꾸면 약 2 GiB다. 이는 직접 계산한 예시이며 특정 제품이나 모델의 실측값이 아니다. GQA 모델에서는 query head 수를 KV head 수로 대입하면 추정이 틀릴 수 있다.

**평가:** GB와 GiB, bit와 byte를 구별한다. 실측한다면 첫 토큰 지연, 생성 토큰당 시간, 입력·출력 토큰 수, 최대 메모리, 요청 수와 답변 정확성을 같은 조건에서 기록한다. 1차 전에는 계산 개념만 이해하고 대형 모델 다운로드는 생략해도 된다.

## 모든 연습에 적용할 검증 기준

### AI가 만든 계산과 설명을 확인하는 순서

1. 데이터의 한 행이 무엇인지, ID가 유일한지, 분모와 단위를 정한다.
2. AI 답변의 숫자를 SQL·짧은 코드·계산기로 재계산한다.
3. 관찰 사실, 모델 예측, 원인 가설, 사람이 결정할 조치를 구분한다.
4. 데이터가 시간적으로 앞선 정보인지 확인하고 분할 정책을 정한다.
5. 기존 방식이나 단순 기준선과 비교한 뒤 결과와 한계를 기록한다.

특히 다음 오류는 짧은 문제에서도 점수를 크게 왜곡할 수 있다.

| 오류 | 바로 확인할 예 |
| --- | --- |
| 가중치 없는 평균 | 제품 A 10개 수율 100%, B 990개 수율 90%의 전체 수율은 95%가 아니라 90.1% |
| 비율과 퍼센트포인트 혼동 | 90%에서 91%는 1%p 상승이며 상대 상승률은 약 1.11% |
| 시간 정보 누수 | 공정 전에 불량을 예측하는데 공정 후 최종 검사값을 입력에 포함 |
| 라벨 누수 | 고장 전체 타깃을 예측하면서 개별 고장 모드 타깃을 특성에 포함 |
| 동일 객체 누수 | 같은 웨이퍼의 회전 이미지나 같은 센서 주기의 겹치는 창을 train과 test에 분산 |
| 불균형 지표 오류 | 정상 비율이 매우 높은데 정확도만 보고 불량 recall을 생략 |
| 단위 오류 | K와 섭씨, rpm과 rad/s, Gbps와 GB/s, ms와 s를 혼용 |
| 원인 단정 | 특정 설비와 불량의 상관만으로 그 설비를 원인이라고 확정 |
| 문서 버전 오류 | 같은 제목의 옛 절차를 현재 절차 대신 인용 |

이 표의 숫자는 설명용 계산이다. 실제 대회 규칙이 평가 지표나 분할을 지정하면 그 규칙을 우선 적용한다. 시계열의 미래 자료가 학습에 들어가는 위험과 데이터 간격에 대한 주의는 [scikit-learn TimeSeriesSplit 문서](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)에 설명돼 있다.

## 자료 선택과 학습 순서

**1차 전 2~3시간 도메인 학습의 예:** 메모리와 용어에 30분, GaiA 실제 사례에 30분, 생산 CSV 집계와 로그 근거 확인에 60~120분을 쓴다. 준비 시간 자체가 짧으면 먼저 30분짜리 개념만 읽고 AI 기초·검증 연습으로 돌아간다. 전체 시간에서 20%를 넘기지 않도록 조정한다.

**1차 이후:** 관심에 따라 문서·로그 도우미를 확장하거나 SECOM·AI4I·Hydraulic 중 하나만 끝까지 수행한다. 웹 개발 강점을 살리려면 근거 검색, 업로드 데이터 검사, 결과 검토 UI와 내보내기를 먼저 다듬고, 모델 성능 개선은 그다음에 한다.

**본선 대비:** 실제 공개 규칙과 제공 데이터가 확인된 뒤 데이터 형식, 외부 API, 네트워크, GPU, 사전 코드 사용, 제출 형식에 맞춰 구현을 축소하거나 확장한다. 내부 설비 문서와 고객 데이터에 대한 접근을 가정하는 사전 준비는 필요하지 않다.

데이터 라이선스와 배포 상태는 `semiconductor-sources.json`에 함께 기록했다. UCI의 명확한 CC BY 4.0 자료와 자체 합성 자료가 바로 연습하기 쉽고, WM-811K와 MVTec은 권리·제출 조건 확인을 별도로 잡아야 한다.
